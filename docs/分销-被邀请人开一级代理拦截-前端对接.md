# 分销-被邀请人开一级代理拦截恢复-前端对接

> 后端改动（2026-09-23）：`PATCH /api/admin/users/:id/invite-config` 恢复「被邀请用户不能开一级分销代理」的 400 拦截。
> 前端用户管理页已去掉被邀请人的开关，本文档只需关注**兜底 400 的展示**——接口仍可能被直接调用，400 文案要原样透出。

## 变更点（只有一个接口）

`PATCH /api/admin/users/:id/invite-config`（权限点 `management.users`，用户管理页邀请配置弹窗在调的那个）

### 新拦截规则

请求体 `canInvite: true`，且目标用户是被邀请人（`invitedById` 非空）、当前邀请权处于关闭状态时：

| 条件 | 结果 |
|------|------|
| 其邀请人 `canInvite=true` 且 `subInviteAllowed=true`（上级已开「下级可继续邀请」） | ✅ 放行，正常返回 |
| 其它（上级没开邀请 / 没开「下级可继续邀请」） | ❌ **400** |

### 400 响应体

```json
{
  "statusCode": 400,
  "message": "该用户由 上级分销 邀请注册，不能开一级分销代理；如需让他继续邀请下级，请在【客户运营·分销管理】里对 上级分销 开启「下级可继续邀请」。",
  "timestamp": "2026-09-23T08:00:00.000Z"
}
```

- `message` 中的两处用户名是**动态**的（邀请人用户名），前端**不要自己拼文案**，直接把 `message` toast / 弹窗透出即可
- 这与全局异常过滤器的标准错误结构一致（`statusCode` / `message` / `timestamp`），复用现有错误处理就行

### 不受影响的场景（保持现状，无需改动）

- `canInvite: false`（关闭）：不拦截，被邀请人关闭一切正常（单人关闭后端打 `canInviteManualOff` 标记）
- 请求体**不带 `canInvite` 字段**（只改折扣、返利比例、名额等）：完全不受影响
- 平台直签用户（非被邀请人）开/关：完全不受影响
- 已经被开着的被邀请人（存量数据）重复提交 `canInvite: true`：幂等放行，不报 400（不影响存量行保存其它配置）

## 前端建议处理

1. 用户管理页被邀请人行的「允许邀请注册」开关：**保持已去掉的状态**（后端拦截是兜底，不是替代）
2. 邀请配置弹窗的保存按钮：如果弹窗里其它字段（折扣/返利等）和 `canInvite` 是**分开提交**的，无需任何改动；如果是**合并提交**，注意别给被邀请人带上 `canInvite: true`
3. 收到 400 时：直接展示后端 `message`（文案里已引导运营去【客户运营·分销管理】对邀请人开「下级可继续邀请」）

## 自测用例对照（后端已验证）

| 用例 | 预期 |
|------|------|
| 平台直签用户开/关邀请 | 正常 |
| 被邀请人，上级未开「下级可继续邀请」，开启 | 400，message 如上 |
| 被邀请人，上级本人邀请权已关，开启 | 400，message 如上 |
| 被邀请人，上级已开「下级可继续邀请」，单独关后再开 | 成功，`manualOff` 标记被清除（上级以后批量打开能覆盖到此人） |
| 被邀请人关闭邀请权 | 成功 |

## 其它说明

- 接口路径、请求体结构、权限点（`management.users`）均无变化
- 「下级可继续邀请」开关（`subInviteAllowed`）的既有拦截不变：被邀请用户不可开（400「被邀请用户不可开启『下级可继续邀请』（分销网络最多两级）」）

# 一键上架功能—部署说明

> 本文说明一键上架的配置和运行机制。生产执行顺序以 `docs/一键上架部署20260803.md` 为准。

## 1. 功能范围

本版本包含：

- 店铺、全局分类目录、店铺分类及模板 URL。
- 仅生产环境每天从指定飞书多维表格视图同步店铺。
- 仅生产环境每天主动请求 RPA 获取尚未就绪的店铺分类模板。
- 提交 Amazon 上架、用户主动刷新处理结果。
- RPA 查询结果回调落库后，通过按 JWT 用户隔离的 SSE 通知前端。
- 每 5 分钟主动查询上架中任务。
- 飞书同步、RPA Cron 运行和每次 RPA 请求的可追溯日志。

RPA 的三种动作全部由后端调用影刀 `startTask`。该接口只返回影刀 `taskUuid`/`jobUuidList`，表示脚本已被调起。RPA 执行完成后使用 `X-API-Key` 将业务结果 POST 到 `/api/product-publish/internal/rpa/results`。`rpa_storage` 是影刀官方未定义含义的保留字段，当前固定传空字符串，不是结果接口地址。

## 2. 环境变量

### 2.1 飞书店铺同步

```dotenv
FEISHU_APP_ID=""
FEISHU_APP_SECRET=""
FEISHU_BITABLE_APP_TOKEN="F8a8bVmq0aTfgVshLkBc5fxQnOd"
FEISHU_BITABLE_TABLE_ID="tblDhqrTSPiS003m"
FEISHU_BITABLE_VIEW_ID="vewkPm0nDO"
FEISHU_BASE_URL="https://open.feishu.cn"
```

飞书应用必须具有读取目标多维表格的权限，并已成为该表格协作者。`FEISHU_APP_ID` 和 `FEISHU_APP_SECRET` 必须同时填写；同时留空表示关闭飞书同步。

### 2.2 一键上架影刀调度

```dotenv
YINGDAO_ACCESS_KEY_ID=""
YINGDAO_ACCESS_KEY_SECRET=""
YINGDAO_BASE_URL="https://api.yingdao.com"

YINGDAO_PRODUCT_PUBLISH_TASK_UUID=""
YINGDAO_PRODUCT_PUBLISH_APP_ID=""
YINGDAO_PRODUCT_PUBLISH_PARAM_NAME="paramsFile"
YINGDAO_PRODUCT_PUBLISH_PROFILE="dev"
YINGDAO_PRODUCT_PUBLISH_RUN_TIMEOUT_SECONDS="3600"
YINGDAO_PRODUCT_PUBLISH_TEMPLATE_BATCH_RUN_TIMEOUT_SECONDS="10800"
YINGDAO_PRODUCT_PUBLISH_MAX_POLL_ATTEMPTS="288"
YINGDAO_PRODUCT_PUBLISH_CALLBACK_API_KEY=""
YINGDAO_PRODUCT_PUBLISH_CALLBACK_TIMEOUT_SECONDS="4200"
```

含义：

- `YINGDAO_PRODUCT_PUBLISH_TASK_UUID`：影刀任务 ID，请求时映射到 `scheduleUuid`，不是 Cron 配置。
- `YINGDAO_PRODUCT_PUBLISH_APP_ID`：已发布的一键上架应用 ID，映射到 `robotUuid`。
- `YINGDAO_PRODUCT_PUBLISH_PARAM_NAME`：文件类型流程入参名，默认 `paramsFile`。
- `YINGDAO_PRODUCT_PUBLISH_PROFILE`：当前后端环境，必填且只允许 `dev`、`dev1`、`uat`、`prod`；每次启动影刀时以 `{name:"profile", type:"string"}` 传入，同时控制飞书/模板每日 Cron 仅在 `prod` 执行。
- `YINGDAO_PRODUCT_PUBLISH_RUN_TIMEOUT_SECONDS`：影刀单次脚本运行超时秒数。
- `YINGDAO_PRODUCT_PUBLISH_MAX_POLL_ATTEMPTS`：结果查询最大次数，默认 288 次（每 5 分钟一次，约 24 小时）。
- `YINGDAO_PRODUCT_PUBLISH_CALLBACK_API_KEY`：RPA 提交业务结果时的 `X-API-Key`，一键上架 RPA 启用时必填高强度随机值。
- `YINGDAO_PRODUCT_PUBLISH_CALLBACK_TIMEOUT_SECONDS`：调度后等待 RPA 业务结果的超时秒数，默认 `4200`，必须至少比脚本运行超时多 60 秒。

一键上架后端不使用 `API_BASE_URL` 生成结果地址；RPA 部署时单独配置完整的生产 API 域名和上述 API Key。项目中现有 `API_BASE_URL`/`RPA_CALLBACK_TOKEN` 属于其他 RPA 功能，不得与一键上架配置混用。

各环境分别配置：开发环境 `dev`、第二开发环境 `dev1`、验收环境 `uat`、生产环境 `prod`。不要直接复用 `NODE_ENV`，因为其常见值 `development/production` 与 RPA 约定不一致。

## 3. 数据库变更

增量 migrations（必须按顺序执行）：

```text
prisma/migrations/20260803000000_product_publish_store_rpa/migration.sql
prisma/migrations/20260803010000_product_publish_rpa_callback/migration.sql
prisma/migrations/20260804000000_product_publish_task_skus/migration.sql
```

主要模型：

- `ProductPublishStore`：店铺主表，飞书店铺 ID 按字符串保存。
- `ProductPublishClassificationCatalog`：全局分类目录。
- `ProductPublishStoreClassification`：店铺分类与永久模板 URL。
- `ProductPublishFeishuSyncRun/Record`：飞书批次和逐行审计。
- `ProductPublishRpaRun`：模板任务和轮询任务每次运行的汇总日志。
- `ProductPublishRpaLog`：每次影刀调度、异步业务结果、两阶段耗时和错误。
- `ProductPublishTask`：增加 `PUBLISHING`、Amazon `uploadId`、成功/失败数、文件 URL、首次提交时冻结的 `skus` JSON、SKU-ASIN JSON 和轮询字段。

历史任务的 `publishStoreId` 保留为 `null`，不使用旧店铺名文本猜测关联。

RPA 请求日志状态为 `DISPATCHING → WAITING_CALLBACK → PROCESSING_CALLBACK → SUCCESS/FAILED`；在 `WAITING_CALLBACK` 超过配置时间则进入 `TIMEOUT`。影刀调度成功只代表进入 `WAITING_CALLBACK`，不代表 Amazon 业务成功。

已建立 Prisma migration 基线的环境使用：

```bash
npm run db:deploy
```

历史上只使用 `prisma db push` 的环境，必须备份数据库并由 DBA/运维核对 diff 后沿用既有路径。不得直接重置数据库或伪造 migration 历史。

## 4. 初始化脚本

数据库结构升级后依次执行：

```bash
# 1. 检查并将现有分类码下划线替换为空格
npm run normalize:product-publish-classifications
npm run normalize:product-publish-classifications -- --apply

# 2. 检查初始 12 分类，不写库
npm run import:product-publish-classifications -- \
  ./scripts/product-publish-classifications.initial.json

# 3. 幂等写入分类并为现有店铺补齐分类
npm run import:product-publish-classifications -- \
  ./scripts/product-publish-classifications.initial.json \
  --apply

# 4. 立即同步指定飞书视图
npm run sync:product-publish-stores
```

未来新增分类仍使用分类导入脚本，先 dry-run，再加 `--apply`。脚本保留已有模板 URL 和 RPA 信息。

分类文本只允许大写字母、数字和单个空格；原下划线必须替换为空格，例如 `NOTEBOOK_COMPUTER → NOTEBOOK COMPUTER`。本项目使用 `prisma db push`，该变化由独立数据修正脚本完成。需要把全部店铺分类映射交给 RPA 同事时，再执行第二个独立脚本：

远程 MySQL 优先直接执行 `scripts/normalize-product-publish-classifications.sql`，该 SQL 在一个事务内批量更新分类目录、店铺分类、任务和 RPA 日志，并在末尾返回四张表的残留数量。Node 修正命令仅作为没有数据库控制台时的兜底。

```bash
npm run export:product-publish-store-classifications
```

导出文件默认是 `temp/product-publish-store-classifications.json`，每项严格只包含 `externalStoreId`、`classification`。也可用 `-- --output <路径>` 指定文件；如果数据库仍是下划线格式或错误的无分隔符格式，导出脚本会拒绝执行。

## 5. 定时任务

| 任务 | Cron | 时区 | 行为 |
| --- | --- | --- | --- |
| 飞书店铺同步 | `0 10 2 * * *` | `Asia/Shanghai` | 仅 `profile=prod`：先拉取完整指定视图，再按店铺 ID 新增/更新 |
| 店铺模板刷新 | `0 10 3 * * *` | `Asia/Shanghai` | 仅 `profile=prod`：主动执行 `download_listing` |
| Amazon 结果轮询 | `0 */5 * * * *` | `Asia/Shanghai` | 所有环境：主动执行 `check_feed_status` |

四个 Cron 都开启 `waitForCompletion=true`，用于防止同一进程内上一次未完成时重叠执行。`dev/dev1/uat` 每天触发前两个 Cron 时只记录跳过日志，不读取飞书、不请求模板；每 5 分钟结果轮询仍处理各自数据库中的上架任务。生产多实例部署时仍需确保只有一个 Cron 执行实例，或配置分布式租约。

手工命令 `npm run sync:product-publish-stores` 和 `npm run sync:product-publish-templates` 不受 Cron 环境限制，联调环境需要时仍可由运维显式执行。全量模板脚本每次都会按店铺聚合后批量重新调度全部店铺分类；旧的待回调模板请求会先结束并释放，正在写库的回调则等待事务结束后继续，不会跳过分类。

飞书同步规则：

- 只读指定 `view`；
- 先拉取完所有分页，再做数据库更新；
- 按 `externalStoreId` 幂等新增/更新；
- 视图中缺失的本地店铺保留，不删除、不自动禁用；
- 每条飞书记录单独写审计结果，一条失败不得中断整批。

## 6. RPA 业务契约摘要

输入通过 `paramsFile` 文件参数传递：

```json
[
  {
    "business_type": "Amazon",
    "business_id": "27826971599669",
    "tasks_info": [
      {
        "task_type": "check_feed_status",
        "task_id": "",
        "rpa_storage": "",
        "task_param": {
          "upload_id": "6b1ccdde-16f4-41e4-99d1-5d1ff273c02d",
          "skus": ["SKU-001", "SKU-002"]
        }
      }
    ]
  }
]
```

影刀 `startTask` 成功时只返回调度标识。RPA 执行完成后 POST 到 `/api/product-publish/internal/rpa/results`，请求头为 `X-API-Key: <YINGDAO_PRODUCT_PUBLISH_CALLBACK_API_KEY>`，请求体为：

```json
{
  "contract_version": "1.0",
  "ok": true,
  "data": {
    "task_type": "upload_listing",
    "business_id": "27826971599669",
    "file_url": "https://files.example.com/product-publish/listing.xlsm",
    "upload_id": "6b1ccdde-16f4-41e4-99d1-5d1ff273c02d"
  }
}
```

`request_id` 为可选交叉校验字段。后端主要按业务键找回内部日志：模板为 `business_id + category`，提交为 `business_id + file_url origin/pathname`，查询为 `business_id + upload_id`。`check_feed_status.task_param.skus` 来自首次提交时冻结在 `ProductPublishTask.skus` 的原始 SKU JSON 列表。

完整字段和示例见 `docs/一键上架-RPA对接.md`。

## 7. 部署后验证

使用有效 JWT：

```bash
curl -H "Authorization: Bearer <JWT>" \
  https://<API域名>/api/product-publish/stores

curl -H "Authorization: Bearer <JWT>" \
  'https://<API域名>/api/product-publish/records?page=1&pageSize=10&storeId=27826971599669'
```

上架链路：

```bash
curl -X POST \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{"fileUrl":"https://files.example.com/product-publish/listing.xlsm","skus":["SKU-001","SKU-002"]}' \
  https://<API域名>/api/product-publish/tasks/<taskId>/publish

curl -X POST \
  -H "Authorization: Bearer <JWT>" \
  https://<API域名>/api/product-publish/tasks/<taskId>/publish/refresh

# 保持连接，验证会先收到 connected，之后持续收到 heartbeat/业务事件
curl -N \
  -H "Accept: text/event-stream" \
  -H "Authorization: Bearer <JWT>" \
  https://<API域名>/api/product-publish/events
```

SSE 反向代理必须关闭响应缓冲并延长读取超时。Nginx 对该接口至少配置：

```nginx
location = /api/product-publish/events {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
}
```

当前业务事件总线位于 Node 进程内。单实例部署可直接使用；多实例部署必须将 SSE 路由和一键上架 RPA 回调路由固定到同一业务实例，或接入 Redis Pub/Sub 后再水平扩容。前端仍应保留任务详情低频轮询作为断线降级。

RPA 结果接口联调（必须先完成一次真实调度，并使用完全一致的业务键）：

```bash
curl -X POST \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <YINGDAO_PRODUCT_PUBLISH_CALLBACK_API_KEY>' \
  -d '{"contract_version":"1.0","ok":true,"data":{"task_type":"upload_listing","business_id":"27826971599669","file_url":"https://files.example.com/product-publish/listing.xlsm","upload_id":"6b1ccdde-16f4-41e4-99d1-5d1ff273c02d"}}' \
  https://<API域名>/api/product-publish/internal/rpa/results
```

验收重点：

- `/stores` 只返回未禁用 Amazon 店铺，店铺 ID 为字符串。
- 模板刷新成功后 `templateStatus=SUCCESS`，`templateUrl` 可公开下载。
- `/publish` 异步返回 `accepted=true`，表示后端已受理并永久锁定本次提交；影刀接收结果可能已确认，也可能因网络异常暂时未知。等待回调时任务保持 `COMPLETED` 但 `submitRequestId` 已非空并永久禁止重提。RPA 回传 Amazon `upload_id` 后，后端同时写入 `uploadId` 并把任务改为 `PUBLISHING`。
- `/publish/refresh` 异步返回后端已受理一次查询启动尝试；影刀接收结果可能已确认或暂时未知，Amazon 结果稍后由 RPA 提交。
- RPA 查询结果回调事务提交后，SSE 收到 `product-publish-refresh-completed`；事件的 `taskId`、`requestId` 与刷新响应一致。
- `ProductPublishRpaLog` 区分“影刀已确认接收/启动结果未知”和“RPA 业务结果已接收”等阶段，不把启动尝试当作业务成功。
- 同一 `ProductPublishTask` 第二次调用 `/publish` 返回 `409`。
- `/publish.fileUrl` 必须对应当前任务已完成的 `spreadsheetUrl`；同一店铺和表格对象由数据库唯一键阻止重复提交。

## 8. 排障顺序

1. 飞书问题：先看最新 `ProductPublishFeishuSyncRun`，再按 `runId` 看 `ProductPublishFeishuSyncRecord`。
2. Cron 未执行：查看 `ProductPublishRpaRun` 是否有对应时间的运行记录。
3. 影刀请求失败：按 `requestId` 查 `ProductPublishRpaLog`，核对 `taskUuid`/`jobUuidList`。
4. 调度成功但未收到业务结果：核对 RPA 脚本日志、结果 URL/API Key 及 `YINGDAO_PRODUCT_PUBLISH_CALLBACK_TIMEOUT_SECONDS`。
5. 业务结果拒绝：核对 `contract_version`、`request_id`、`task_type`、`business_id`和各动作字段。
6. `uploadId` 异常：确认该值来自 Amazon `upload_listing` 结果，不是影刀调度标识。

上架请求返回不明时不得为同一任务再次提交 Amazon，只能通过后端内部 `requestId`、店铺 ID、文件 URL 和请求日志排查；业务文件中的 `task_id` 始终为空字符串。


## 2026-10-27 模板刷新调整

- 每日 03:10 按店铺汇总到期类目，上传一个 JSON 参数文件并调用一次影刀 `startTask`；同店铺放同一个 `tasks_info`，不同店铺放外层数组。
- 仅 `prod` 新增 `30 */5 * * * *` 失败扫描：失败满 5 分钟后重新发起下载，初次 + 最多 3 次自动重试。成功/进行中类目不补发，次日刷新重新计数。
- RPA 必须遍历整批并逐类目回调，不能仅执行第一条，也不能仅返回整批结果。对接示例见 [RPA 协议 §3.1](./一键上架-RPA对接.md#31-模板下载批量示例)。
- 批量运行超时默认 10800 秒，由 `YINGDAO_PRODUCT_PUBLISH_TEMPLATE_BATCH_RUN_TIMEOUT_SECONDS` 调整；回调窗口在此基础上增加普通回调与运行超时的差值（默认 600 秒）。普通单任务仍用原配置。
- 刷新中或失败时，前端解析、步骤跳转、下载和导出使用最近成功保存的模板；不按当天文件名或最新任务 SUCCESS 状态卡住。首次从未下载成功的类目仍没有可用模板。
- 无新增数据库字段，不需要执行数据库结构同步。前后端代码均需发布；实际发布由运维手工执行。本次代码测试不代表 RPA 脚本已完成真实批量联调。


### 配置缺失错误不自动重试

失败补发扫描遇到当前 `lastSyncError` 或最新下载日志中包含「未查询到店铺」「传入密码为空」时，跳过该类目，不新建下载请求，不清空最近成功的模板 URL、成功时间或错误信息。页面仍可使用已保存模板；从未成功下载且没有模板 URL 的情况无法凭空恢复文件。普通登录失败、网络错误和超时仍按原重试策略处理。每日正常刷新与手工刷新保持可用，以便店铺或账号配置修复后重新获取模板。已经提交给 RPA 的运行中批次不受此跳过规则影响。

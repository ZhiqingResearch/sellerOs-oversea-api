# 选品分析记录分步保存开发技术方案（V2）

> 适用范围：选品工具「逛类目找机会」五步分析、分析记录恢复、商品库入库。
>
> 后端项目：NestJS + Prisma + MySQL。
>
> 本文是对《选品分析记录_分步追加式后端对接方案》的落地修订版。

## 1. 结论

原方案的核心结构可行：一次分析使用一条主记录，每一步使用一条独立步骤记录；不同步骤追加，同一步骤保存当前有效版本。它比把五步累计数据放进一个 JSON 字段并反复整体覆盖更安全。

落地前需要修正以下关键问题：

1. 当前项目的 `User.id` 是 `Int`，原方案中的 `VARCHAR user_id` 与现有外键不兼容。
2. 原方案的 `PUT` 每次都会增加 `revision`，并可能删除下游步骤，网络重试并不是真正幂等。
3. 主表虽有 `version`，但保存逻辑未实际比较版本，无法阻止旧页面覆盖新结果。
4. 上游步骤重复提交时不应无条件清除下游；只有步骤内容实际变化时才能使下游失效。
5. 第一步也存在重新生成场景，步骤保存接口必须支持 `stepNo=1`，不能只支持第 2～5 步。
6. `currentStep` 容易被理解成“当前要操作的步骤”，建议改名为 `lastCompletedStep`，明确表示当前有效的最高已完成步骤。
7. JSON 字段可以保存步骤产物，但不能完全放弃结构校验；列表查询、状态、计数、去重所需字段必须结构化保存。
8. `pickCount` 不应直接信任前端，应由第五步结果计算，或至少与第五步结果交叉校验。
9. 当前服务全局请求体上限是 5 MB；原方案写“每步 2 MB”不会自动生效，需要显式做字节数校验。
10. 当前全局异常过滤器只返回 `statusCode/message/timestamp`，会丢掉原方案设计的业务 `code/details`。
11. 商品库若按“分析 ID + 关键词 + ASIN”作为商品唯一键，同一商品会在列表中重复出现，标签和备注也会分散。
12. 新软删除模型必须加入 `src/prisma/prisma.service.ts` 的 `SOFT_DELETE_MODELS`。

最终采用以下结构：

```text
SelectionAnalysisRecord（一次分析）
├── SelectionAnalysisStep（第 1 步）
├── SelectionAnalysisStep（第 2 步）
├── SelectionAnalysisStep（第 3 步）
├── SelectionAnalysisStep（第 4 步）
└── SelectionAnalysisStep（第 5 步）

ProductLibraryItem（用户商品库中的唯一商品）
└── ProductLibrarySnapshot（来自某次分析、某个关键词的画像快照，可多条）
```

## 2. 范围与兼容策略

### 2.1 本期实现

- 第一步创建分析记录并保存步骤 1。
- 第 1～5 步结果的覆盖式保存。
- 内容未变化时幂等返回，不增加版本、不删除下游。
- 内容变化时使下游步骤失效。
- 分析记录列表、详情恢复、软删除。
- 商品库单个/批量入库、列表、详情、标签备注编辑、软删除。
- 用户数据归属校验、步骤顺序校验、并发版本校验、请求体大小校验。

### 2.2 不改动现有模块

以下现有接口继续保留，不直接复用或改表：

- `ProductReport` / `/api/product-report`：现有通用产品报告，不具备分步结构。
- `SelectedProduct` / `/api/selected-product/batch`：目前只保存 `productCode`，不足以承载商品画像。

新功能单独建模，避免影响已有调用方。历史数据是否迁移待确认旧 `ProductReport.data` 的实际结构后再单独处理。

## 3. 核心业务约定

1. 一次分析只有一个 `analysisId`。
2. 第一步创建成功后前端必须拿到 `analysisId`，再保存后续步骤。
3. 每个 `analysisId + stepNo` 最多一条当前有效步骤记录。
4. 每次只提交当前步骤结果，不提交其他步骤数据。
5. 同一步骤内容相同的重复请求是无副作用成功：不增加 `revision/version`，不清除下游。
6. 同一步骤内容实际变化时更新该步骤、`revision + 1`，并删除其后的所有步骤。
7. 每次发生有效变更时主表 `version + 1`；请求必须携带 `expectedVersion`。
8. 步骤必须连续，默认不允许跳步。
9. `lastCompletedStep` 表示当前有效的最高已完成步骤，不表示页面下一步。
10. 前端恢复后，下一步为 `min(lastCompletedStep + 1, 5)`；已完成时展示第 5 步。
11. 第五步成功后状态为 `COMPLETED`；任一上游步骤变化导致第五步被删除后回到 `PROCESSING`。
12. 分析记录保存和商品库入库是两件事：第五步自动保存在分析记录中，用户执行“存入商品库”时才创建商品库快照。

## 4. Prisma 数据模型

字段命名与当前项目保持 Prisma 风格，`userId` 使用现有 `Int` 外键。`analysisId` 对前端是不透明字符串，建议使用 UUID。

```prisma
enum SelectionAnalysisEntry {
  CATALOG
  PRODUCT
}

enum SelectionAnalysisStatus {
  PROCESSING
  COMPLETED
}

enum SelectionAnalysisStepType {
  CATEGORY_DIAGNOSIS
  TRACK_VALIDATION
  COMPETITOR_POOL
  TRAFFIC_AD_VALIDATION
  PRODUCT_LIST
}

model SelectionAnalysisRecord {
  id                  String                  @id @default(uuid()) @db.VarChar(36)
  userId              Int
  user                User                    @relation(fields: [userId], references: [id])
  clientRequestId     String                  @db.VarChar(64)
  createFingerprint   String                  @db.VarChar(64)
  marketplace         String                  @db.VarChar(16)
  entry               SelectionAnalysisEntry  @default(CATALOG)
  primaryCategoryNodeId String?                @db.VarChar(255)
  primaryCategoryPath String?                  @db.VarChar(1000)
  primaryCategoryName String?                  @db.VarChar(500)
  categories          Json
  lastCompletedStep   Int                     @default(1)
  pickCount           Int                     @default(0)
  status              SelectionAnalysisStatus @default(PROCESSING)
  version             Int                     @default(1)
  createdAt           DateTime                @default(now())
  updatedAt           DateTime                @updatedAt
  deletedAt           DateTime?
  steps               SelectionAnalysisStep[]
  productSnapshots    ProductLibrarySnapshot[]

  @@unique([userId, clientRequestId])
  @@index([userId, deletedAt, updatedAt])
  @@index([userId, marketplace, deletedAt, updatedAt])
}

model SelectionAnalysisStep {
  id            Int                       @id @default(autoincrement())
  analysisId    String                    @db.VarChar(36)
  analysis      SelectionAnalysisRecord   @relation(fields: [analysisId], references: [id], onDelete: Cascade)
  stepNo        Int
  stepType      SelectionAnalysisStepType
  schemaVersion Int                       @default(1)
  payload       Json
  payloadHash   String                    @db.VarChar(64)
  revision      Int                       @default(1)
  createdAt     DateTime                  @default(now())
  updatedAt     DateTime                  @updatedAt

  @@unique([analysisId, stepNo])
  @@index([analysisId])
}

model ProductLibraryItem {
  id          Int                      @id @default(autoincrement())
  userId      Int
  user        User                     @relation(fields: [userId], references: [id])
  marketplace String                   @db.VarChar(16)
  asin        String                   @db.VarChar(32)
  title       String?                  @db.VarChar(1000)
  brand       String?                  @db.VarChar(255)
  imageUrl    String?                  @db.VarChar(2048)
  tags        Json?
  notes       String?                  @db.Text
  latestKeyword      String?           @db.VarChar(500)
  latestCompScore    Decimal?          @db.Decimal(10, 4)
  latestPrice        Decimal?          @db.Decimal(12, 2)
  latestMonthlySales Int?
  latestRatingNum    Int?
  createdAt   DateTime                 @default(now())
  updatedAt   DateTime                 @updatedAt
  deletedAt   DateTime?
  snapshots   ProductLibrarySnapshot[]

  @@unique([userId, marketplace, asin])
  @@index([userId, deletedAt, updatedAt])
  @@index([userId, marketplace, deletedAt, latestCompScore])
}

model ProductLibrarySnapshot {
  id               Int                      @id @default(autoincrement())
  itemId           Int
  item             ProductLibraryItem       @relation(fields: [itemId], references: [id], onDelete: Cascade)
  sourceAnalysisId String                   @db.VarChar(36)
  sourceAnalysis   SelectionAnalysisRecord  @relation(fields: [sourceAnalysisId], references: [id], onDelete: Restrict)
  keyword          String                   @db.VarChar(500)
  compScore        Decimal?                 @db.Decimal(10, 4)
  price            Decimal?                 @db.Decimal(12, 2)
  monthlySales     Int?
  ratingNum        Int?
  profile          Json
  profileHash      String                   @db.VarChar(64)
  createdAt        DateTime                 @default(now())
  updatedAt        DateTime                 @updatedAt

  @@unique([itemId, sourceAnalysisId, keyword])
  @@index([sourceAnalysisId])
  @@index([itemId, updatedAt])
}
```

```prisma

```

### 4.1 数据库约束

Prisma Schema 不能完整表达的约束应写进 migration SQL：

```sql
ALTER TABLE `SelectionAnalysisRecord`
  ADD CONSTRAINT `chk_selection_last_completed_step`
  CHECK (`lastCompletedStep` BETWEEN 1 AND 5),
  ADD CONSTRAINT `chk_selection_pick_count`
  CHECK (`pickCount` >= 0),
  ADD CONSTRAINT `chk_selection_version`
  CHECK (`version` >= 1);

ALTER TABLE `SelectionAnalysisStep`
  ADD CONSTRAINT `chk_selection_step_no`
  CHECK (`stepNo` BETWEEN 1 AND 5),
  ADD CONSTRAINT `chk_selection_schema_version`
  CHECK (`schemaVersion` >= 1),
  ADD CONSTRAINT `chk_selection_revision`
  CHECK (`revision` >= 1);
```

### 4.2 关于 `tenantId/orgId`

当前项目是 `UserOrganization` 多对多关系，JWT 中没有明确的当前组织上下文，因此本期不存 `tenantId`。

如果后续分析记录需要组织共享，必须先定义“当前组织”的来源，并校验用户组织成员关系；届时增加 `orgId Int` 外键，唯一键和所有查询条件也要加入 `orgId`。不能接受前端直接传一个未经校验的租户 ID。

### 4.3 软删除

只对可独立访问的主资源软删除：

- `SelectionAnalysisRecord`
- `ProductLibraryItem`

两者必须加入 `SOFT_DELETE_MODELS`。步骤和画像快照不提供独立删除，不增加 `deletedAt`；读取前先校验其父资源。

分析记录软删除不会删除商品库画像。画像快照需要保留来源，因此外键采用 `ON DELETE RESTRICT`；未来若要物理清理分析记录，必须先制定画像快照归档或清理策略，不能直接删除来源主记录。

`monthlySales/ratingNum` 使用 `Int` 是为了避免 Prisma `BigInt` 直接进入 JSON 响应时的序列化问题。当前业务计数上限足够时优先使用 `Int`；若未来确实可能超过 32 位整数，再改成 `BigInt`，并在所有响应 DTO 中统一转换为字符串。

唯一键不会因为软删除自动释放：

- 已软删除分析的 `clientRequestId` 不允许再次创建；命中时返回 `ANALYSIS_ALREADY_DELETED`，前端开启新分析必须生成新的 `clientRequestId`。
- 已软删除商品再次入库时恢复原 `ProductLibraryItem`（`deletedAt=null`），保留原标签备注，再新增或更新来源画像，不创建重复商品。

当前软删除扩展只覆盖挂在 `PrismaService` 上的模型读委托。事务客户端是否继承扩展不能作为业务正确性的前提，因此所有 transaction 内的主资源查询仍必须显式写 `deletedAt: null`。需要查询已删除行处理唯一键冲突时，使用参数化 `$queryRaw` 或专门的“含已删除记录”访问方法，不能拼接 SQL。

## 5. JSON 单字段设计结论

每一步使用一个 `payload Json` 字段是合适的，但只适用于“整块写入、整块恢复、内部字段基本不参与 SQL 查询”的结果数据。

### 5.1 必须结构化保存的字段

以下字段不能只藏在 JSON 中：

- 用户归属：`userId`
- 创建幂等：`clientRequestId/createFingerprint`
- 列表筛选：`marketplace/entry/primaryCategoryName/primaryCategoryPath`
- 流程状态：`lastCompletedStep/status/version`
- 列表摘要：`pickCount`
- 步骤控制：`stepNo/stepType/schemaVersion/revision/payloadHash`
- 商品去重与排序：`asin/marketplace/keyword/compScore/price` 等

### 5.2 JSON 字段的风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 任意对象绕过业务校验 | 按 `stepNo` 校验顶层必需键、数据类型、数组数量和字符串长度 |
| 大 JSON 占用内存和带宽 | 保存前按 UTF-8 字节数校验，列表永不读取 `payload` |
| 更新 JSON 会重写整个字段 | 每步独立一行；只在生成完成后保存完整步骤结果，不做高频局部写 |
| 前端结构升级后旧记录无法恢复 | 保存 `schemaVersion`，详情接口原样返回，前端提供版本适配器 |
| 相同内容被当作新版本 | 对规范化 JSON 计算 SHA-256 `payloadHash` |
| JSON 内字段难以检索 | 需要筛选/排序的字段提升为结构化列，不依赖 JSON path 做核心查询 |

不建议把五步产物重新合并进主表的一个 `data` 字段，也不建议把每一个业务子对象都拆成关系表。当前“一步一 JSON + 少量摘要列”是复杂度与可维护性之间较合适的边界。

## 6. 步骤数据契约与校验

后端不能只做 `@IsObject()`。每一步至少校验下列顶层结构，具体上限在与前端类型确认后固化为常量：

| 步骤 | 必需字段 | 最低校验 |
| --- | --- | --- |
| 1 | `diagnosis` | 数组、数量上限、每项必须为对象 |
| 2 | `oppResults`、`selectedKeywords` | 结果数组；关键词为去重后的非空字符串数组 |
| 3 | `compResults`、`selectedAsinsByKeyword` | 结果数组；ASIN 映射必须为对象，总 ASIN 数有限制 |
| 4 | `anaResult` | 非空对象 |
| 5 | `reportData` | 非空对象；必须能提取最终入选商品数组 |

建议上限：

- `selectedKeywords <= 50`
- 单个关键词长度 `<= 500`
- 竞品/ASIN 总数 `<= 500`
- 单步骤序列化后 `payload <= 4 MiB`
- `schemaVersion` 当前只接受 `1`

当前 `src/main.ts` 已配置全局 JSON 请求体 5 MB。服务层仍需执行：

```ts
const bytes = Buffer.byteLength(JSON.stringify(payload), "utf8")
if (bytes > STEP_PAYLOAD_MAX_BYTES) {
  throw new PayloadTooLargeException({
    code: "ANALYSIS_PAYLOAD_TOO_LARGE",
    message: "当前步骤数据超过 4 MiB，请减少关键词或竞品数量",
  })
}
```

网关/Nginx 的请求体上限必须不低于应用的 5 MB，否则请求会在到达 NestJS 前被拒绝。

### 6.1 `pickCount`

优先方案：不接收独立的 `pickCount`，从第五步 `reportData` 中的最终入选商品数组计算。

如果前端当前结构无法稳定提取，则请求暂时保留 `pickCount`，但必须满足：

- 非负整数；
- 有业务上限；
- 与 `reportData` 中可识别的商品数一致，不一致返回 `400`；
- 后端只把校验后的值写入主表。

在前后端联调前需要明确第五步最终商品数组的唯一字段路径，例如 `reportData.items`，不能同时支持多个含义模糊的候选字段。

## 7. API 设计

所有路径由全局前缀自动形成 `/api/...`。

### 7.1 创建分析并保存第一步

```http
POST /api/product-selection/analysis-records
Authorization: Bearer <token>
```

```json
{
  "clientRequestId": "0a49d1d3-84e7-43a0-8a68-c24f0ed93d27",
  "marketplace": "US",
  "entry": "CATALOG",
  "primaryCategoryNodeId": "xxx",
  "categories": [
    {
      "nodeId": "xxx",
      "nodeIdPath": "A:B:C",
      "name": "Cup Holders",
      "nameCn": "杯架"
    }
  ],
  "schemaVersion": 1,
  "payload": {
    "diagnosis": []
  }
}
```

后端根据 `primaryCategoryNodeId` 从 `categories` 中提取主类目摘要，避免前端分别传名称、路径后产生不一致。

成功响应：

```json
{
  "analysisId": "uuid",
  "stepNo": 1,
  "revision": 1,
  "lastCompletedStep": 1,
  "pickCount": 0,
  "status": "PROCESSING",
  "version": 1,
  "idempotentReplay": false,
  "createdAt": "2026-08-20T00:00:00.000Z",
  "updatedAt": "2026-08-20T00:00:00.000Z"
}
```

### 7.2 保存或重新保存任一步骤

步骤接口支持 `stepNo=1..5`：

```http
PUT /api/product-selection/analysis-records/{analysisId}/steps/{stepNo}
```

```json
{
  "expectedVersion": 3,
  "schemaVersion": 1,
  "payload": {}
}
```

第五步不再单独传前四步数据。若暂时不能从 `reportData` 计算计数，可在第五步请求中增加受校验的 `pickCount`。

响应：

```json
{
  "analysisId": "uuid",
  "stepNo": 3,
  "revision": 2,
  "lastCompletedStep": 3,
  "pickCount": 0,
  "status": "PROCESSING",
  "version": 4,
  "changed": true,
  "invalidatedSteps": [4, 5],
  "updatedAt": "2026-08-20T00:00:00.000Z"
}
```

内容完全相同时返回 `changed=false`，数据库版本不变化，下游步骤不失效。

### 7.3 列表、详情和删除

```http
GET    /api/product-selection/analysis-records
GET    /api/product-selection/analysis-records/{analysisId}
DELETE /api/product-selection/analysis-records/{analysisId}
```

列表查询 DTO 继承现有 `PaginationDto`，增加：

- `marketplace?: string`
- `status?: PROCESSING | COMPLETED`
- `keyword?: string`，仅匹配结构化的主类目名称/路径

列表只查主表摘要。详情返回主表和按 `stepNo ASC` 排列的步骤。删除使用软删除并通过 `@HttpCode(204)` 返回空响应。

### 7.4 商品库

```http
POST   /api/product-library/items
POST   /api/product-library/items/batch
GET    /api/product-library/items
GET    /api/product-library/items/{id}
PATCH  /api/product-library/items/{id}
DELETE /api/product-library/items/{id}
```

第五步通常会一次入库多个产品，因此批量接口应作为首期必需接口，而不是可选项。建议单批最多 100 个，事务内逐个执行商品 upsert 和画像快照 upsert。

入库语义：

- `ProductLibraryItem` 按 `userId + marketplace + asin` 去重，列表中一个商品只出现一次。
- 若唯一商品已软删除，再次入库时恢复该商品；恢复过程不覆盖已有 `tags/notes`。
- 再次从其他分析存入同一商品时，不覆盖用户的 `tags/notes`。
- `ProductLibrarySnapshot` 按 `itemId + sourceAnalysisId + keyword` 保存来源画像。
- 同一来源和关键词重复入库、画像内容相同时幂等返回；内容变化时更新快照。
- 商品详情返回商品信息、标签备注和画像快照列表；列表默认只返回最新画像的摘要，不返回完整 `profile`。
- 商品主表冗余最新画像的关键词、评分、价格、销量和评论数，保证列表分页后仍能按最新评分正确排序；每次画像入库在同一事务中同步这些摘要。

入库前统一规范化：`asin=trim().toUpperCase()`、`marketplace=trim().toUpperCase()`、`keyword=trim()` 并合并连续空白；Amazon ASIN 按 `^[A-Z0-9]{10}$` 校验。价格、评分、销量、评论数必须为非负值。Prisma `Decimal` 在 API 响应中应通过响应 DTO 明确转换，不能让前端猜测其最终是字符串还是数字。

## 8. 创建幂等

后端对创建请求中除 `clientRequestId` 外的业务字段做稳定 JSON 序列化，并计算 SHA-256 `createFingerprint`。

处理规则：

1. `userId + clientRequestId` 不存在：事务内创建主表和步骤 1。
2. 已存在且指纹一致：返回原记录，`idempotentReplay=true`。
3. 已存在但指纹不同：返回 `409 CLIENT_REQUEST_ID_REUSED`，不能静默返回旧分析。
4. 已存在但已软删除：返回 `409 ANALYSIS_ALREADY_DELETED`，不能恢复分析或绕过唯一键创建新记录。
5. 两个相同创建请求并发时，以数据库唯一键为最终保障；捕获 `P2002` 后查询包含已删除行的原记录，并按上述规则返回。

这可以避免网络超时重试产生重复分析，也能避免前端错误复用 UUID 后拿到不相关的旧分析。

## 9. 步骤保存事务与并发控制

### 9.1 内容哈希

不能直接对普通 `JSON.stringify()` 结果计算哈希，因为对象键顺序可能不同。应先递归排序对象键、保持数组顺序，再计算 SHA-256：

```text
hashInput = canonicalJson({ schemaVersion, payload })
payloadHash = sha256(hashInput)
```

数组顺序通常具有业务意义，不排序数组。

### 9.2 事务算法

先在事务外完成 DTO 校验、大小校验、规范化 JSON 和哈希计算，减少持锁时间。然后在一个 Prisma interactive transaction 中完成：

```text
1. 按 id + userId + deletedAt=null 查询并锁定分析主记录。
2. N > 1 时校验第 N-1 步存在；不存在返回 409。
3. 读取当前第 N 步记录。
4. 如果当前步骤 payloadHash、schemaVersion 和第五步摘要均未变化：
   - 直接返回 changed=false；
   - 不比较 expectedVersion；
   - 不增加 revision/version；
   - 不删除下游步骤。
5. 内容有变化时，比较 record.version === expectedVersion；不一致返回 409。
6. 查询 stepNo > N 的现有步骤号，用于返回 invalidatedSteps。
7. 删除 stepNo > N 的步骤。
8. upsert 第 N 步；已存在则 revision + 1。
9. 更新主表：
    - lastCompletedStep = N
    - version = version + 1
    - N=5：status=COMPLETED，pickCount=服务端计算值
    - N<5：status=PROCESSING，pickCount=0
10. 提交事务并返回新 version。
```

内容相同的判断必须在版本冲突判断之前。这样网络超时后的相同请求即使携带旧 `expectedVersion`，也能安全返回成功；若数据已被其他请求真正修改，哈希不同，再由版本比较阻止旧请求覆盖新结果。

### 9.3 锁与 Prisma 实现

必须防止两个请求同时读到同一个旧版本。可以采用以下任一实现，并写并发测试验证：

方案 A（推荐）：事务内通过参数化 `$queryRaw` 对主记录执行 `SELECT ... FOR UPDATE`，后续全部使用同一事务客户端。

方案 B：先用带 `id/userId/version/deletedAt` 条件的 `updateMany` 做 Compare-And-Swap，`count=0` 时返回版本冲突，再执行步骤更新。

不能只在内存中比较版本后直接 `update`，否则并发请求仍可能同时通过校验。

## 10. 状态不变量

任意事务提交后必须满足：

```text
步骤号从 1 连续到 lastCompletedStep，不允许中间缺失；
lastCompletedStep = 当前最大有效 stepNo；
lastCompletedStep = 5  <=> status = COMPLETED；
status = COMPLETED     => pickCount = 第五步最终商品数量；
status = PROCESSING    => pickCount = 0；
主表每次有效变化 version + 1；
步骤每次有效变化 revision + 1；
无内容变化的重试不修改 updatedAt/version/revision。
```

## 11. 鉴权、权限与错误响应

### 11.1 数据归属

所有分析和商品库读写都必须带当前 `userId` 条件。不存在、已删除、不属于当前用户统一返回 `404`，避免泄露资源存在性。

不要复制当前 `ProductReportService.findById()` 只按 ID 查询的做法；新服务统一使用 `findFirst({ where: { id, userId } })` 或等价的复合条件。

### 11.2 功能权限

保存和恢复分析属于选品工作台流程，首期建议复用现有：

```text
tool.flow_workbench
```

如果新增“选品分析记录”和“商品库”管理菜单，需要先确认谁可访问。当前 `PermissionsGuard` 的规则是持有 `management.product` 会自动获得所有 `management.product.*` 子权限；若不希望自动授权，应像现有敏感词权限一样，使用不落在 `management.product.*` 命名空间下的 key，仅通过 `parentKey` 把菜单显示在产品管理下。

不要只新增 permission seed 而不考虑该继承规则。

### 11.3 错误结构

建议统一为：

```json
{
  "statusCode": 409,
  "code": "ANALYSIS_VERSION_CONFLICT",
  "message": "分析记录已在其他页面更新，请刷新后重试",
  "details": {
    "expectedVersion": 3,
    "currentVersion": 4
  },
  "timestamp": "2026-08-20T00:00:00.000Z"
}
```

需要同步修改 `AllExceptionsFilter`：当 `HttpException.getResponse()` 是对象时，保留其中的 `code/details`，不要只提取 `message`。若系统需要 `requestId`，必须先在日志中间件创建并挂载请求 ID，再由异常过滤器返回；不能在方案里声明一个当前不存在的字段。

主要错误码：

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `INVALID_STEP_NO` | 步骤编号无效 |
| 400 | `INVALID_STEP_PAYLOAD` | 步骤结构或数量不合法 |
| 404 | `ANALYSIS_NOT_FOUND` | 分析不存在、已删除或无权访问 |
| 409 | `CLIENT_REQUEST_ID_REUSED` | 创建幂等键被用于不同内容 |
| 409 | `ANALYSIS_ALREADY_DELETED` | 创建幂等键对应的分析已被删除 |
| 409 | `PREVIOUS_STEP_NOT_COMPLETED` | 前一步不存在 |
| 409 | `ANALYSIS_VERSION_CONFLICT` | 并发版本冲突 |
| 413 | `ANALYSIS_PAYLOAD_TOO_LARGE` | 步骤 JSON 超限 |
| 404 | `PRODUCT_LIBRARY_ITEM_NOT_FOUND` | 商品库记录不存在或无权访问 |

## 12. 前端对接要求

1. 第一步生成完成后创建 `clientRequestId`，请求失败重试时继续使用同一个值；开启新分析时必须生成新值。
2. 第一步保存必须等待成功并取得 `analysisId/version`。
3. 后续保存携带详情或上次保存响应中的最新 `expectedVersion`。
4. 同一分析的保存请求默认串行，不能让多个步骤无序提交。
5. `analysisId` 写入 URL；`sessionStorage` 只作为辅助，URL 是刷新恢复入口。
6. 页面刷新后调用详情接口，恢复每一步 payload 和最新 `version`。
7. 本地重新生成第 N 步后可以先隐藏下游结果，但最终以保存响应的 `invalidatedSteps` 为准。
8. 收到 `ANALYSIS_VERSION_CONFLICT` 时停止自动覆盖，提示刷新/重新载入，不自动重试变更请求。
9. 显示“保存中 / 已保存 / 保存失败可重试”。
10. 前端按 `schemaVersion` 做旧数据适配，未知版本展示明确的不兼容提示。

## 14. 测试与验收

### 14.1 分析记录

- 创建主记录和步骤 1 必须在同一事务中。
- 相同 `clientRequestId + 相同内容` 重试只返回原记录。
- 相同 `clientRequestId + 不同内容` 返回 409。
- 相同步骤、相同内容重复 PUT 不增加版本，不删除下游。
- 上游步骤内容变化时只删除其后的步骤，并正确返回失效步骤号。
- 只有步骤 1 时提交步骤 3 返回 409。
- 第 1 步允许通过统一步骤接口重新保存。
- `expectedVersion` 过期且内容变化时返回 409。
- 两个并发更新只有一个成功，另一个返回版本冲突。
- 第五步计数由结果正确计算，完成状态正确。
- 用户 A 无法查询、更新、删除用户 B 的分析。
- 软删除后列表和详情均不可见，商品库快照仍存在。
- 超过单步骤大小和各数组数量上限时被拒绝。

### 14.2 商品库

- 同一用户、站点、ASIN 只产生一个 `ProductLibraryItem`。
- 同一商品可以拥有多个来源分析/关键词画像快照。
- 重复入库不会覆盖用户标签和备注。
- 批量入库部分数据非法时按既定策略整体回滚；首期建议整体回滚并返回具体下标。
- 列表不返回完整画像，详情才返回快照 `profile`。
- 用户不能操作他人的商品库数据或使用他人的 `sourceAnalysisId`。

## 15. 推荐开发顺序

1. 与前端确认五步 payload 的真实 TypeScript 类型，尤其是第五步最终商品数组字段。
2. 添加 Prisma 模型和 migration，注册软删除模型。
3. 实现 canonical JSON、哈希、步骤级校验器。
4. 实现创建幂等、步骤事务、版本冲突和下游失效。
5. 实现列表、详情、软删除与错误码保留。
6. 接入前端 URL 恢复和串行保存队列，先跑通五步闭环。
7. 实现商品库主项 + 来源快照和批量入库。
8. 补并发、幂等、权限、大小边界测试。
9. 联调后确认菜单与权限继承范围，再添加 permission seed。

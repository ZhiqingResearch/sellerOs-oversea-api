# 竞品分析记录开发技术方案（V1）

> 适用范围：竞品基础数据、流量与广告、价格与促销分析全部完成后的历史记录归档、查询、详情回显和软删除。
>
> 后端项目：NestJS + Prisma + MySQL；时间口径：`Asia/Shanghai`。
>
> 本文基于《竞品分析记录后端接口需求》及实际业务流程整理。核心业务口径已确认：记录仅创建人可见、后端只保存前端最终结果，数据按“分析记录 → 产品 → 产品步骤结果”三层保存。

## 1. 评审结论

三表方案可行，并且比把全部数据放进主表 JSON 更符合原型的页面层级：

1. `CompetitorAnalysisRecord` 保存本次分析的输入、总体分析结果、最终分析报告和列表摘要。
2. `CompetitorAnalysisProduct` 保存本次记录中的我方产品和各竞品信息。
3. `CompetitorAnalysisProductStep` 保存每个产品的每一步分析结果。

最终报告与一次分析记录是一对一关系，V1 直接把结构化 `reportData` 放在主表，不必再增加报告表。PDF 是报告的导出格式，不把 PDF Base64 或二进制存进 MySQL。前端生成 PDF 后调用现有的独立文件上传接口，上传接口返回文件 URL；竞品分析模块只接收并保存该 URL，不参与文件上传。

原需求可以进入开发，但实现时需要补齐以下技术约束：

| 级别 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| 已确认 | 总体分析、步骤结果和报告暂无内部字段契约 | 后端不能判断业务内容是否完整 | 使用 MySQL `JSON` 列保存对象，只做容量和安全扫描；页面恢复正确性由前端保证 |
| 已确认 | “自动归档”由前端触发 | 用户在首次保存请求发出前关页仍可能漏存 | 前端在总体分析、全部产品步骤和最终报告成功后立即 POST，并以同一 `clientRequestId`、同一请求体做失败重试；后端保证请求级幂等 |
| 已确认 | 记录仅创建人可见 | 不需要组织共享模型 | 所有写入从 JWT 取 `userId`，所有读写条件都包含 `userId`，不保存或使用 `currentOrgId` |
| 高 | `summary` 与 `input` 重复，且由前端提交 | `competitorCount/title` 可能和实际 ASIN 不一致 | 摘要由后端基于规范化后的输入生成；前端摘要不得作为权威数据 |
| 高 | 产品和步骤只放进主表 JSON | 列表搜索、产品顺序、步骤定位和未来扩展都较困难 | 产品与步骤分别建表；完整业务结果仍存各自的 JSON 列 |
| 高 | 前端把步骤结果作为“JSON 字符串”传递 | 容易发生双重编码，后端收到的是字符串而不是 JSON 对象 | 接口必须直接传 JSON 对象；数据库使用 `Json` 类型，不使用 `TEXT` 保存 `JSON.stringify()` 结果 |
| 高 | 未定义请求大小、JSON 深度、图片内容规则 | 容易保存 Base64、DOM、超深 JSON，造成内存和数据库压力 | 总请求快照限制 4 MiB，JSON 最大 30 层，禁止 `blob:`、Base64 图片和 DOM/HTML 页面快照 |
| 中 | `marketplace` 写成“US/UK/DE/JP/MX 等” | “等”无法形成稳定校验和前后端契约 | V1 常量白名单固定为 `US/UK/DE/JP/MX`，数据库用 `VARCHAR`，扩站点时只升级应用契约 |
| 中 | `dateFrom/dateTo` 支持“日期或日期时间”，边界和时区不清晰 | 近 7/30/90 天结果可能少一天或多一天 | V1 只接受 `YYYY-MM-DD`，按北京时间自然日解释，`dateTo` 包含整天 |
| 中 | 软删除后原 `clientRequestId` 如何处理未定义 | 软删除不释放唯一键，重放会产生唯一冲突 | 原请求 ID 永久不可复用，返回专用 409；重新归档必须生成新 UUID |
| 中 | 没有说明记录是否可编辑 | 编辑会破坏历史快照含义和幂等指纹 | V1 不提供更新接口；重新分析创建新记录 |

## 2. V1 业务口径

V1 按以下已确认口径设计：

1. 分析结果由现有前端/现有分析接口生成，本模块只负责归档，不重新执行分析、不调用 AI Provider。
2. 总体分析、全部产品步骤和最终报告生成成功后，前端生成一次 UUID v4 作为 `clientRequestId` 并一次性提交完整三层数据；网络重试复用相同 ID 和相同请求体。
3. 记录属于创建用户，仅本人可查询和删除；本期只使用 `JwtAuthGuard`。
4. 分析输入、结果、产品、步骤和报告内容创建后不可编辑；只允许后续回写或覆盖 `reportPdfUrl`，不提供恢复软删除接口。
5. 查看历史只读取快照，不重新调用分析接口。
6. `analysisResult/productData/step.resultData/reportData` 作为通用 JSON 对象保存，不校验内部业务字段，只进行合法性、容量和安全扫描。
7. 不保存 HTML、DOM、Base64、Blob URL 或浏览器本地对象。
8. 软删除是逻辑删除：输入、分析和报告立即对 API 不可见，但数据库物理空间不会立即释放。

## 4. 数据模型

### 4.1 推荐 Prisma 模型

```prisma
enum CompetitorAnalysisMode {
  ASIN
  KEYWORD
}

model CompetitorAnalysisRecord {
  id                 String                      @id @default(uuid()) @db.VarChar(36)
  userId             Int
  user               User                        @relation(fields: [userId], references: [id], onDelete: Restrict)
  clientRequestId    String                      @db.VarChar(36)
  createFingerprint  String                      @db.Char(64)

  schemaVersion      Int                         @default(1)
  marketplace        String                      @db.VarChar(16)
  mode               CompetitorAnalysisMode
  ownAsin            String?                     @db.Char(10)
  /// 规范化后的竞品 ASIN 摘要，供列表直接返回，避免读取 inputSnapshot
  competitorAsins    Json
  sourceKeyword      String?                     @db.VarChar(500)
  title              String                      @db.VarChar(500)
  productCount       Int
  competitorCount    Int

  /// 原始分析输入，例如输入模式、ASIN 列表、关键词和来源文本
  inputSnapshot      Json
  /// 分析完成后、进入逐产品拆解前展示的总体分析结果
  analysisResult     Json
  /// 最终竞品分析报告；前端据此恢复报告并导出 PDF
  reportData         Json
  /// 前端生成 PDF 并上传 OSS 后回写的访问 URL
  reportPdfUrl       String?                     @db.VarChar(2048)
  reportPdfUpdatedAt DateTime?
  /// 主表、产品和步骤全部 JSON 的 UTF-8 总字节数
  payloadBytes       Int

  version            Int                         @default(1)
  createdAt          DateTime                    @default(now())
  updatedAt          DateTime                    @updatedAt
  deletedAt          DateTime?

  products           CompetitorAnalysisProduct[]

  @@unique([userId, clientRequestId])
  @@index([userId, deletedAt, createdAt])
  @@index([userId, marketplace, deletedAt, createdAt], map: "CompetitorAnalysisRecord_user_market_created_idx")
  @@index([userId, ownAsin, deletedAt, createdAt], map: "CompetitorAnalysisRecord_user_own_asin_created_idx")
}

model CompetitorAnalysisProduct {
  id          Int                      @id @default(autoincrement())
  recordId    String                   @db.VarChar(36)
  record      CompetitorAnalysisRecord @relation(fields: [recordId], references: [id], onDelete: Cascade)
  /// 搜索和产品定位使用；完整产品信息仍以 productData 为准
  asin        String                   @db.Char(10)
  sortOrder   Int

  /// 前端传什么产品信息就保存什么，不校验内部业务字段
  productData Json

  steps        CompetitorAnalysisProductStep[]
  createdAt    DateTime                     @default(now())
  updatedAt    DateTime                     @updatedAt

  @@unique([recordId, asin])
  @@unique([recordId, sortOrder])
  @@index([asin, recordId], map: "CompetitorAnalysisProduct_asin_record_idx")
}

model CompetitorAnalysisProductStep {
  id            Int                       @id @default(autoincrement())
  productId     Int
  product       CompetitorAnalysisProduct @relation(fields: [productId], references: [id], onDelete: Cascade)
  /// 前端提供的稳定步骤代码；后端不维护固定步骤白名单
  stepCode      String                    @db.VarChar(64)
  stepNo        Int
  schemaVersion Int                       @default(1)
  /// 前端直接传 JSON 对象，禁止传 JSON.stringify 后的字符串
  resultData    Json
  payloadHash   String                    @db.Char(64)
  payloadBytes  Int
  createdAt     DateTime                  @default(now())
  updatedAt     DateTime                  @updatedAt

  @@unique([productId, stepCode])
  @@unique([productId, stepNo])
}
```

### 4.2 设计说明

- 主表的 `inputSnapshot/analysisResult/reportData`、产品表的 `productData`、步骤表的 `resultData` 都是不可变 JSON 快照。
- `ownAsin/title/competitorCount` 由服务端从结构化 `input` 提取或生成，`productCount` 由产品数组长度生成，不信任前端重复字段。
- 产品表不区分我方或竞品，也不解析 `productData` 内部字段；前端传入什么产品 JSON 就原样保存什么。
- 产品表保留展示顺序，并可在不读取大 JSON 的情况下搜索我方或任一竞品 ASIN。
- 步骤数量和类型完全以前端为准；后端不限制固定三步，只要求同一产品内 `stepCode` 和 `stepNo` 唯一。
- 前端直接提交 JSON 对象；Prisma 字段使用 `Json`，不能把 `JSON.stringify()` 的结果作为字符串保存，否则会双重编码。
- 列表查询只能选择主表摘要及产品表的 `asin/sortOrder`，不得读取主表大 JSON、`productData` 或步骤数据。
- `payloadBytes` 用于容量审计；`createFingerprint` 用于判断相同幂等键下的内容是否一致。
- 只有主表加入软删除集合；产品和步骤通过未删除主表访问。物理删除主表时才通过外键级联清理子表。
- Migration 增加版本、数量、非负顺序和 `payloadBytes >= 0` 等检查约束；产品与步骤的唯一性同时由数据库唯一键和服务层校验保证。

## 5. 创建接口

```http
POST /api/competitor-analysis/records
```

### 5.1 请求契约调整

创建请求调整为与三层表结构一致。前端一次性提交总体结果、产品数组、每个产品的步骤数组以及最终报告。`summary` 可以兼容接收，但服务端不直接落库，也不把它纳入幂等指纹；详情响应中的摘要根据规范化数据重新构造。

```json
{
  "clientRequestId": "9c82fc0e-f74f-4bb8-9075-223ba56d24aa",
  "schemaVersion": 1,
  "marketplace": "US",
  "input": {
    "mode": "ASIN",
    "ownAsin": "B0AAAA0001",
    "competitorAsins": ["B0BBBB0002", "B0CCCC0003"],
    "keyword": null,
    "sourceText": "https://www.amazon.com/dp/B0AAAA0001"
  },
  "analysisResult": {},
  "products": [
    {
      "asin": "B0AAAA0001",
      "sortOrder": 0,
      "productData": {},
      "steps": [
        {
          "stepCode": "PROFILE",
          "stepNo": 1,
          "schemaVersion": 1,
          "resultData": {}
        },
        {
          "stepCode": "CUSTOM_STEP_FROM_FRONTEND",
          "stepNo": 2,
          "schemaVersion": 1,
          "resultData": {}
        }
      ]
    }
  ],
  "reportData": {}
}
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `clientRequestId` | 必填，UUID v4 |
| `schemaVersion` | 必填，V1 只接受整数 `1` |
| `marketplace` | 必填，trim 后转大写，V1 必须是 `US/UK/DE/JP/MX` 之一 |
| `input.mode` | `ASIN` 或 `KEYWORD` |
| `input.ownAsin` | 可为 `null`；非空时必须是 10 位字母数字，转大写 |
| `input.competitorAsins` | 1～20 个；每项为 ASIN；转大写、去首尾空格、禁止重复，且不得等于 `ownAsin` |
| `input.keyword` | `KEYWORD` 模式必填，`ASIN` 模式为 `null`；最大 500 字符 |
| `input.sourceText` | 可选，最大 20,000 字符 |
| `summary` | 兼容接收；不作为权威数据、不落库、不参与幂等指纹 |
| `analysisResult` | 必填，必须为非数组 JSON 对象；保存总体分析结果 |
| `products` | 必填，非空；产品数量和内容以前端为准，后端不要求与 `input` 的 ASIN 集合完全一致 |
| `products[].asin` | 必填，10 位字母数字；仅用于产品唯一定位和历史搜索 |
| `products[].sortOrder` | 必填非负整数；同一次记录内唯一 |
| `products[].productData` | 必填 JSON 对象，内部字段不校验，按前端传入内容原样保存 |
| `products[].steps` | 必填数组，可为空；前端传多少步就保存多少步 |
| `products[].steps[].stepCode` | 必填非空字符串，最大 64 字符；同一产品内唯一，不设业务白名单 |
| `products[].steps[].stepNo` | 必填非负整数；同一产品内唯一，只用于排序 |
| `products[].steps[].resultData` | 必填 JSON 对象，前端直接传对象，禁止传序列化后的 JSON 字符串 |
| `reportData` | 必填，必须为非数组 JSON 对象；内部字段不做业务校验，原样存入 JSON 列 |

后端生成：

```text
competitorCount = 去重后的 competitorAsins.length
productCount = products.length
title = 有 ownAsin 时：我方 {ownAsin} vs {competitorCount} 个竞品
        无 ownAsin 时：{keyword 或“竞品分析”} · {competitorCount} 个竞品
```

标题规则写入纯函数并添加单元测试，确保列表和详情返回一致。

### 5.2 通用 JSON 安全校验

除字段级 DTO 校验外，递归扫描 `input/analysisResult/productData/resultData/reportData` 中的全部 JSON：

- 整个规范化快照 UTF-8 大小不超过 4 MiB；应用当前全局 Body Parser 上限为 5 MiB。
- JSON 最大嵌套 30 层，使用显式栈扫描，避免递归栈溢出。
- 禁止 `blob:`、`data:image/` 和其他 Base64 文件内容；图片只保存 HTTPS URL。
- 禁止 `dom`、`documentHtml`、`innerHtml`、`outerHtml`、`pageHtml` 等页面快照键。
- 不在日志中输出快照正文，只记录 `recordId/userId/payloadBytes`。

超过上限返回 HTTP 413 和 `COMPETITOR_RECORD_PAYLOAD_TOO_LARGE`。

### 5.3 幂等与并发

1. 先完成 trim、大小写、产品/步骤排序、数组和跨字段规范化。
2. 对除 `clientRequestId` 外的完整规范化内容调用 `hashJson()` 生成 `createFingerprint`。
3. 查询 `(userId, clientRequestId)`：
   - 指纹相同：返回原记录，`idempotentReplay=true`。
   - 指纹不同：返回 409 `CLIENT_REQUEST_ID_REUSED`。
4. 主表、全部产品和全部步骤必须在同一事务中一次性写入；任一行失败则整次回滚，不能留下半条历史记录。
5. 捕获 Prisma `P2002`，重新读取唯一键处理并发创建，不能直接返回 500。
6. 如果唯一键对应的是已软删除记录，返回 409 `COMPETITOR_RECORD_ALREADY_DELETED`；新分析必须换 UUID。

创建和幂等重放统一返回 HTTP 201：

```json
{
  "recordId": "48efab82-71c1-4d4e-a626-5bc0ac351e53",
  "version": 1,
  "createdAt": "2026-08-25T08:00:00.000Z",
  "updatedAt": "2026-08-25T08:00:00.000Z",
  "idempotentReplay": false
}
```

## 6. 列表接口

```http
GET /api/competitor-analysis/records?page=1&pageSize=10&keyword=B0AAAA0001&marketplace=US&dateFrom=2026-08-01&dateTo=2026-08-25
```

查询规则：

- `page/pageSize` 复用 `PaginationDto`，默认 1/10，`pageSize` 最大 100。
- `keyword` trim 后转大写，同时匹配主表 `ownAsin` 和产品表任一 `asin`。
- 关键词为完整 10 位 ASIN 时优先走等值查询；不足 10 位时允许 `contains`，数据量增长后再评估前缀搜索。
- `marketplace` 为精确筛选，并使用同一站点白名单规范化。
- `dateFrom/dateTo` 只接受 `YYYY-MM-DD`，按北京时间自然日解释。
- `dateFrom` 为左闭边界；`dateTo` 转为次日零点并作为右开边界。
- “近 7 天”指含今天在内的 7 个北京时间自然日，前端传今天和前 6 天。
- 排序固定为 `createdAt DESC, id DESC`，避免同毫秒创建时翻页抖动。

列表只选择主表摘要和产品表的 `asin/sortOrder`，不读取 `inputSnapshot/analysisResult/reportData/productData/steps` 等大字段。响应仍沿用需求文档格式；`ownAsin/competitorAsins` 继续使用主表摘要和结构化输入生成，不根据产品内部 JSON 猜测产品角色。

## 7. 详情与删除

### 7.1 详情

```http
GET /api/competitor-analysis/records/:recordId
```

- `recordId` 使用 UUID v4 参数校验。
- 查询条件必须同时包含 `id + userId`，不存在、属于他人或已删除统一返回 404。
- API 将数据库 `inputSnapshot` 映射回 `input`，返回完整的 `analysisResult`、产品与步骤树、`reportData`。
- 产品按 `sortOrder ASC, id ASC` 排序，步骤按 `stepNo ASC, id ASC` 排序，避免依赖数据库默认顺序。
- API 响应中的 `productData/resultData` 均为 JSON 对象，不返回二次编码后的字符串。
- `summary` 由主表摘要字段构造，保证与列表一致。
- 不返回 `userId/createFingerprint/payloadBytes/deletedAt` 等内部字段。
- 不重算、修正或升级历史快照；前端按 `schemaVersion` 选择渲染适配器。

详情响应核心结构：

```json
{
  "recordId": "48efab82-71c1-4d4e-a626-5bc0ac351e53",
  "schemaVersion": 1,
  "version": 1,
  "marketplace": "US",
  "input": {},
  "summary": {},
  "analysisResult": {},
  "products": [
    {
      "productId": 1,
      "asin": "B0AAAA0001",
      "sortOrder": 0,
      "productData": {},
      "steps": [
        {
          "stepCode": "PROFILE",
          "stepNo": 1,
          "schemaVersion": 1,
          "resultData": {}
        }
      ]
    }
  ],
  "reportData": {},
  "reportPdfUrl": "https://cdn.example.com/competitor-analysis/48efab82/report.pdf",
  "reportPdfUpdatedAt": "2026-08-25T08:05:00.000Z",
  "createdAt": "2026-08-25T08:00:00.000Z",
  "updatedAt": "2026-08-25T08:00:00.000Z"

```

### 7.2 回写 PDF URL

PDF 由前端根据 `reportData` 生成。前端自行调用现有文件上传接口，取得上传接口返回的 URL 后调用：

```http
PATCH /api/competitor-analysis/records/:recordId/report-pdf
```

```json
{
  "reportPdfUrl": "https://cdn.example.com/competitor-analysis/48efab82/report.pdf"
}
```

处理规则：

- 使用 `JwtAuthGuard`，查询和更新条件必须包含 `recordId + userId + deletedAt=null`。
- URL 必须是 HTTPS，最大 2048 字符。
- 相同 URL 重复提交按幂等成功处理，不递增版本。
- 新 URL 与当前值不同时允许覆盖，以支持重新生成 PDF；更新 `reportPdfUpdatedAt/updatedAt` 并将 `version` 加一。
- 竞品分析模块只回写 URL，不接收 PDF Base64 或文件二进制，也不调用、代理或实现文件上传。
- 上传接口的路径、文件限制和返回结构由现有文件上传模块负责，不属于本模块契约。

成功响应：

```json
{
  "recordId": "48efab82-71c1-4d4e-a626-5bc0ac351e53",
  "reportPdfUrl": "https://cdn.example.com/competitor-analysis/48efab82/report.pdf",
  "reportPdfUpdatedAt": "2026-08-25T08:05:00.000Z",
  "version": 2,
  "updatedAt": "2026-08-25T08:05:00.000Z",
  "changed": true
}
```

### 7.3 删除

```http
DELETE /api/competitor-analysis/records/:recordId
```

使用带归属条件的原子更新：

```ts
await prisma.competitorAnalysisRecord.updateMany({
  where: { id: recordId, userId, deletedAt: null },
  data: { deletedAt: new Date(), version: { increment: 1 } },
})
```

- 成功返回 HTTP 204，无响应体。
- 不存在、属于他人或已经删除统一返回 404 `COMPETITOR_RECORD_NOT_FOUND`。
- 软删除后主记录、产品和步骤均不再能通过业务 API 访问；产品、步骤不单独提供删除接口。

## 8. 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `INVALID_COMPETITOR_RECORD_PAYLOAD` | 字段、数组或跨字段关系不合法 |
| 400 | `INVALID_REPORT_PDF_URL` | PDF URL 不是合法的 HTTPS 地址 |
| 400 | `UNSUPPORTED_COMPETITOR_RECORD_SCHEMA_VERSION` | 当前不支持该结构版本 |
| 400 | `INVALID_DATE_RANGE` | 日期无效或起始晚于结束 |
| 401 | 无固定业务 code | Token 缺失、失效或账号停用 |
| 404 | `COMPETITOR_RECORD_NOT_FOUND` | 不存在、已删除或无权访问 |
| 409 | `CLIENT_REQUEST_ID_REUSED` | 同一幂等键对应不同内容 |
| 409 | `COMPETITOR_RECORD_ALREADY_DELETED` | 幂等键对应记录已经软删除 |
| 413 | `COMPETITOR_RECORD_PAYLOAD_TOO_LARGE` | 规范化快照超过限制 |

错误响应沿用全局过滤器：`{ statusCode, code?, message, details?, timestamp }`，所有用户提示使用中文。

## 11. 已确认口径与 V1 默认值

1. **可见范围**：仅创建人可见，不按组织共享。
2. **归档责任**：后端只保存前端最终结果；前端负责在分析完成后触发归档和失败重试。
3. **JSON 契约**：`analysisResult/productData/resultData/reportData` 仅作为通用 JSON 对象保存，后端不校验内部业务字段。
4. **容量默认值**：单条规范化快照最大 4 MiB，禁止 Base64、Blob、DOM 和 HTML 页面快照。
5. **站点默认值**：V1 支持 `US/UK/DE/JP/MX`，后续通过应用常量扩展。
6. **删除语义**：按原需求执行软删除；数据对业务 API 立即不可见，不立即物理清除。
7. **产品数据**：产品表不区分角色、不限制内部字段；前端传入的 `productData` 原样保存。
8. **步骤数据**：不限制步骤类型和数量；前端传多少步就保存多少步，只校验关联、顺序、唯一性和 JSON 安全。
9. **PDF 流程**：前端生成 PDF 并调用现有文件上传接口，取得上传接口返回的 URL 后回写主记录；竞品分析模块不处理上传，数据库不保存 PDF 本体。
10. **可变字段**：分析输入、总体结果、产品、步骤和报告内容创建后不可修改；只有 `reportPdfUrl` 允许后续回写或覆盖。

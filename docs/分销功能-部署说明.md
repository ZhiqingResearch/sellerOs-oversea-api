# 分销功能 — 部署说明

> 适用范围：在**已部署「充值与团队功能」**的环境上增量上线分销（多级邀请 / 返利计提与提现 / 分销管理后台 / 企业池返利逐人开关）。
> 前置环境（充值版已具备的）不重复赘述：Stripe 在线收银台、`MAIL_FROM`/`MAIL_FROM_ALIAS`/`MAIL_DM_ENDPOINT` 邮件通道、短信 `ACCESS_KEY_ID`/`ACCESS_KEY_SECRET`、JWT、Prisma + MySQL（`db push` 同步机制）。
> 前端对接细节（接口/字段/口径逐条）见《分销功能-前端对接.md》，本文只讲部署动作。

执行顺序一览：

1. 拉代码
2. 确认环境变量（**无新增**，复用充值版）
3. 同步数据库结构（db push，无手工 DDL）
4. （分销前端页面一起上线才做）灌分销菜单权限键
5. （条件性，分销首次部署=跳过）一次性数据脚本
6. 构建并启动
7. 按「上线后验证」清单验收

---

## 1. 拉代码

分销代码合并到目标分支并拉取最新（`chao/develop` 分销系列提交：邀请权落库制、企业池返利、PACK/CUSTOM 企业成员拦截、关系树池卷起等）。

## 2. 环境变量

**无新增**。两个依赖通道复用既有配置，缺了会这样表现：

| 通道 | 变量（既有） | 分销侧用在哪 | 未配置后果 |
| --- | --- | --- | --- |
| 邮件 | `MAIL_FROM` / `MAIL_FROM_ALIAS` / `MAIL_DM_ENDPOINT` | 被邀注册的**邮箱验证码**（邀请注册唯一验证通道） | 发送验证码抛 503，被邀注册不可用，其余功能正常 |
| 短信 | `ACCESS_KEY_ID` / `ACCESS_KEY_SECRET` | 既有登录验证码等（分销不直接用） | 既有功能既有表现 |

> 无 Stripe/webhook/域名类新增配置。邀请链接形如 `https://<前端域名>/invite?ref=<邀请码>`，是**前端路由**，前端部署即可，后端无需配域名。

## 3. 同步数据库结构

无手工步骤。Docker 入口自动执行 `prisma db push --accept-data-loss --skip-generate`（**务必先备份数据库**）；手动部署则 `npx prisma db push`。

分销相关的表/列（全部自动同步，仅供核对）：`RebateRule`（全局返利规则单行，**不落库读默认**：企业池计返利开、最多 2 层、无封顶；**2026-09-01 起 `maxLayers` 列改可空**，null=不限计酬层级——纯列可空化，无数据脚本）、`InviteApplication`（被邀注册申请）、`EmailCode`（邮箱验证码）、`User` 的邀请返利列（`canInvite`/`inviteCode(-ExpiresAt)`/`inviteQuota`/`subInviteAllowed`/`canInviteManualOff`/`rebateEnabled`/`rebateRate`/`level2RebateRate`/`shareCreditsWithInvitees`/`corpPassUp`）、`Team.invitedById`（企业邀请链快照）等。

## 4. 分销菜单权限键（仅分销前端页面一起上线时需要）

一次性脚本，只补两个键并绑到内置 ADMIN 角色；**键已存在则整行跳过**（不覆盖后台手调的 route/label），自定义角色绑定不动（要授权去角色管理勾）：

```bash
npx tsx scripts/seed-distribution-permissions.ts --dry-run   # 先看影响面
npx tsx scripts/seed-distribution-permissions.ts             # 正式执行
```

- `management.distribution`：分销管理（落在客户运营页 tab）
- `tool.distribution`：邀请分销（C 端独立页）
- 幂等，可重跑。不要用全量 `prisma/seed.ts rbac` 代替——全量会把种子里所有键回写，覆盖后台手工调整。

## 5. 一次性数据脚本（条件性）

两个脚本都幂等、先 `--dry-run` 再看要不要正式跑。**生产若是分销首次部署（此前没有派生制/池返利代码运行过），两个都是空跑，直接跳过**；若环境（如 dev2）运行过 2026-09-01 前的版本并产生了数据，则**先部署新代码、再跑**：

```bash
# ① 派生邀请权落库：仅当环境跑过「读时派生」版本（2026-09-01 前）且有下级靠派生享受邀请权
#    不跑的话这些下级上线后失去邀请权（他们的 canInvite 从未落库）
npx tsx scripts/backfill-sub-invite.ts --dry-run
npx tsx scripts/backfill-sub-invite.ts

# ② 存量池返利行回填 teamId：仅当环境已产生过企业池返利（REBATE_IN）
#    不跑的话历史池返利不参与分销树的「企业管理员节点池卷起」（返利生成/提现不受影响）
npx tsx scripts/backfill-rebate-team-id.ts --dry-run
npx tsx scripts/backfill-rebate-team-id.ts
```

## 6. 构建与启动

与充值版相同：`npm run build` / Docker 镜像构建部署（db push 已在入口内）。无新增定时任务——分销不新增 `@Cron`（返利计提在消费事务内同步完成；积分清零/订单收口等任务都是充值版既有）。

## 7. 上线后验证

按序过一遍（建议准备一个平台管理员账号 + 两个测试手机号）：

1. **开通分销**：后台用户管理/分销管理给账号 A 开「允许邀请注册」（设返利比例/名额）；A 的钱包出现邀请返利入口，能复制邀请链接/邀请码。
2. **被邀注册链路**：邀请链接打开注册页（邀请码自动带入）→ 邮箱验证码（**验证邮件通道**）→ 提交生成待审申请 → A 在「被邀注册申请审批」通过 → 新账号可登录 + 200 注册赠送积分（GIFT，30 天）。
3. **返利计提**：被邀请人充值包/消费 → A 的「我的返利收益」按 `rebateRate` 入账（**最多 4 位小数不抹零**，1×30%=0.3）；「返利提现」可提。
4. **二级网络**：A 开「下级可继续邀请」→ 其一级下级**批量**获得邀请权+邀请码（落库制）；单人关闭某下级后，上级重开开关**不覆盖**该下级；上级关闭开关 → 下级批量收回。
5. **分销管理后台**（`management.users` 权限点）：关系树（含企业管理员节点池卷起：池消耗/池返利归属与根部收益对平）、全局返利规则（含成本试算 preview）、被邀申请审批队列（运营代审）、邀请配置弹窗扩展数据。
6. **企业池返利**：被邀请人 B 是企业管理员时，管理员在 A 的邀请配置弹窗把 B 的「进企业后仍计返利」打开 → B 企业成员消耗**企业池**积分 → A 收返利；成员**个人**积分消耗仍只走成员自己的邀请链（无邀请人不返）。
7. **企业成员充值拦截**：占用中企业成员（含管理员）下单/支付个人充值包/自定义充值 → 400「你已归属企业团队，不可购买个人充值…」。

## 8. 回滚注意

- **数据层面不删表/列**（db push 不回滚列）；回滚代码即可，新列闲置无副作用。
- 功能层面停用分销：后台把各分销代理的「允许邀请注册」关闭（停止新邀请与计佣）即可；**历史返利（REBATE 桶）保留且可继续提现**（提现不卡邀请权限）。

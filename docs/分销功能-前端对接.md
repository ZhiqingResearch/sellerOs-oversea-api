# 分销功能 — 前端对接文档

> 本文档可直接喂给 AI 用于前端联调。覆盖：邀请注册（公开）、邀请人侧（我的邀请 / 下级管理 / 申请审批 / 返利提现）、后台分销管理（返利规则 / 关系树 / 导出）、后台邀请配置。
> 接口统一前缀 `/api`，除 §3 标注「公开」外均需 Bearer JWT。本文所有字段均以后端源码实际返回为准。
> 分销为第二批上线功能；第一批（充值 / 收据 / 钱包 / 企业团队）见姊妹篇《充值与团队功能-前端对接.md》。被邀请人侧的积分明细「扣费来源细分 / 可用邀请人额度」展示见上一版《积分体系-邀请额度共享-前端对接.md》（仍然有效，本文不重复）。

## 1. 概览

### 1.1 本次新口径（与旧邀请体系的区别，先读这里）

- **邀请只是关系，不是等级**：LV4（FOUNDER）/ LV5（INVITER）特殊计费身份已取消。审批通过的被邀请人 = **普通用户**（`NONE`，可自助订阅 / 充值）；邀请人本身可以同时是 LV1-3 会员。等级枚举里不会再出现 FOUNDER / INVITER。
- **后台开通邀请不再清零套餐积分、不再撤订阅**，只发邀请码（24h 有效）。
- **返利多级上溯**：被邀请人消费时，沿 `invitedById` 自动给上级计提返利，默认 2 层（全局规则可调，1~5 层）。第 1 层比例 = 该邀请人自己的 `rebateRate`，第 2 层 = 其 `level2RebateRate`（`null` 用全局默认 0.10）；某层 `rebateEnabled=false` 则跳过该层、链不断。每层金额**保留最多 4 位小数、不抹零**（2026-08-31 起；1×30% 返 0.3。此前逐笔取整会把不足 1 积分抹成 0，该口径已作废），单笔合计与单月封顶均不超配。**前端注意：返利相关金额可能出现小数，展示格式化（如保留 2 位）自行处理，接口返回原始值字符串**。
- **返利进 REBATE 桶**：独立核算、永不过期、**不可消费**，只能提现（§4.6）；钱包可消费余额不含它。
- **邀请名额**：`inviteQuota`（审批通过计 1）；`null` = 不限。名额用尽时审批通过、开通邀请都会 400。

### 1.2 全流程时序（邀请 → 注册 → 审批 → 消费 → 返利）

```text
邀请人                          被邀请人                        后端
 │  GET /membership/invite       │                              │
 │◀── 邀请码(24h)+名额+待审批 ───▶│                              │
 │── 分享链接 ?code=OS8K3F ─────▶│ 打开链接                      │
 │                               │ GET /invite/verify（校验码）  │
 │                               │ POST /invite/send-email-code │
 │                               │ POST /invite/register        │
 │◀── 待审批出现（§4.1 重新拉）───│◀── applicationId PENDING ────│
 │  POST .../applications/:id/approve                           │
 │                               │ 手机号+密码登录（普通用户）     │
 │                               │── 消费 ─────────────────────▶│ 沿邀请链自动计提返利（REBATE 桶）
 │  POST /membership/rebate/withdraw（提现，平台线下打款）         │
```

## 2. 通用约定

### 2.1 请求头

```http
Authorization: Bearer <JWT>
Content-Type: application/json
```

### 2.2 错误格式

```ts
interface ApiError {
  statusCode: number
  message: string | string[] // 参数校验失败时为数组
  timestamp: string
}
```

本节常见状态码：

| 状态码 | 含义 |
|---|---|
| 400 | 业务校验失败（邀请码失效、验证码错、名额已满、申请已处理等），message 为中文可直接 toast |
| 401 | 未登录 / token 失效 / 账号已停用 → 跳登录 |
| 403 | 未开邀请权限（`当前账号未开启邀请权限`）；操作非自己邀请的下级；后台接口缺权限点（`缺少权限：用户管理` / `无后台充值权限`） |
| 404 | 资源不存在（申请不存在、用户不存在） |
| 409 | 冲突（邀请注册手机号已注册 / 重复申请等） |

### 2.3 分页与积分

- 请求：`page`（默认 1）、`pageSize`（默认 10，最大 100），均为 query 数字。
- 响应：`{ items, total, page, pageSize, totalPages }`。
- 积分数量：Prisma Decimal 序列化为**字符串**（如 `"5600"`），可能带小数位，前端按需 `Math.floor(Number(x))` 展示。

## 3. 邀请注册（公开，无 JWT）

| 接口 | 说明 |
|---|---|
| `GET /api/invite/verify?code=OS8K3F` | 校验邀请码 → `{ "valid": true, "inviterId": 9, "inviterName": "王老板" }`；无效/过期 400「无效链接（邀请码不存在或已过期）」（前端展示「链接已失效」页） |
| `POST /api/invite/send-email-code` | `{ "email": "a@b.com" }` → `{ "sent": true }`；60s 限频（400「验证码获取过于频繁」），前端做倒计时按钮。验证码 5 分钟有效；**连续输错 5 次当前码即作废**，需重新获取（前端在错误提示里引导「重新获取验证码」） |
| `POST /api/invite/register` | 见下 |

**注册 Body**：

```jsonc
{
  "inviteCode": "OS8K3F",     // 4-32 位
  "username": "张三",          // 1-50 字
  "email": "a@b.com",
  "phone": "18800000000",     // 1[3-9] 开头 11 位
  "emailCode": "123456",      // 6 位邮箱验证码
  "password": "Passw0rd!"     // ≥6 位
}
```

**Response 200**：`{ "applicationId": 31, "status": "PENDING" }` → 前端展示「已提交，待邀请人审核」。审核通过后用手机号+密码登录。

**失败**：400 验证码错/邀请码失效；409「该手机号已注册」/「该手机号已提交注册申请，待审核，请勿重复提交」/「已提交申请，请等待邀请人审核」。

**前端处理要点**：注册页从 URL 取 `code` 参数预填邀请码，进入页面先调 `verify`，失效直接展示「链接已失效」页，不渲染表单。

## 4. 邀请人侧

> 未开邀请权限的账号调本节接口返回 403「当前账号未开启邀请权限」——前端据此隐藏入口（例外：§4.6 提现不卡邀请权限，2026-08-31 起，见下）。
> 邀请人资格由平台后台开通（§6），前端无自助开通入口。
> 分销身份判定一律用钱包接口的顶层 `canInvite`（《充值与团队功能-前端对接.md》§7.1，2026-08-30 起），不要只看 `identity==="DISTRIBUTOR"`（团队身份会遮蔽）。
> C 端「邀请/分销」独立页（P8）的菜单权限键为 `tool.distribution`（2026-08-30 起 seed 下发，页面建好补路由）。

**有效邀请权 = 本人 `canInvite` 落库值（2026-09-01 起落库制，废 8-30 读时派生）**：

- 邀请权一律看本人记录上的 `canInvite`：后台单独开通（一级分销），或上级打开「下级可继续邀请」时被**批量打开**（二级邀请人）。钱包顶层 `canInvite`、邀请接口 403、注册校验、返利计酬全链路同读这个落库值。
- **批量打开**：上级开 `subInviteAllowed` 时，其全部一级下级落库 `canInvite=true` 并各自发 24h 邀请码（过期访问 `GET /membership/invite` 自动重生）；**人工单独关过的下级**（`canInviteManualOff=true`）跳过、保持关闭。
- **批量收回**：上级关 `subInviteAllowed`（或上级本人邀请权限被关，连带收回开关）时，一级下级批量 `canInvite=false` + 清邀请码 + 连带关返利（`rebateEnabled=false`）——不打人工标记，上级**重开开关即恢复**（返利随批量打开一并恢复 `rebateEnabled=true`，2026-09-03 bug31 起；与单人开关同口径）。
- **单人开关放开**：管理员可对任意用户（含被邀请用户）单独开/关「允许邀请注册」（§6，8-31 的「被邀请用户不可直开 400」已废）；单人关闭打 `canInviteManualOff` 标记，单人再开清除。
- **开关开着时新审批通过的下级**落库即带邀请权 + 邀请码。
- **网络只到二级**：被邀请用户不可开「下级可继续邀请」（§6 传 `subInviteAllowed: true` 返回 400「被邀请用户不可开启…分销网络最多两级」）；无邀请权的用户也不可开（400「请先开启该用户的『允许邀请注册』」）。
- 存量派生数据由后端脚本 `scripts/backfill-sub-invite.ts` 一次性落库（部署后跑），之后不再存在「记录里 false 但有效」的状态。

**2026-08-31 收紧/修正（QA P0 批）**：

- **被邀请用户不可后台直开一级**（⚠️ 2026-09-01 第七批已废除此拦截，管理员可对任意用户单独开/关，见下文落库制）：`PATCH /admin/users/:id/invite-config` 对 `invitedById` 非空账号传 `canInvite: true` 曾返回 400。现行口径：单人关打 `canInviteManualOff` 标记（上级批量打开时跳过），单人开清除。
- **停用账号邀请码立即失效**：邀请人 `isActive=false` 后，公开校验/邀请注册对其旧邀请码一律 400「无效链接」（启用后自动恢复）。
- **提现不再卡邀请权限**：关闭 `canInvite` 只停新增邀请与后续计佣，历史 REBATE 返利保留可提——`POST /membership/rebate/withdraw` 与超管代发 `POST /admin/recharge/rebate-withdraw` 均不再校验邀请权（REBATE 桶不可消费、提现是唯一出口，锁死即永久沉淀）；可提现余额仍由后端校验。用户侧其它邀请接口（我的邀请/审批/下级管理等）仍要求有效邀请权，403 不变。
- **「本月」口径统一北京自然月**：返利月封顶、钱包本月已用、分销树本月消耗/返利、团队本月已消耗与配额懒重置、用量分析本月/上月筛选，全部按 Asia/Shanghai 切月（容器 UTC 时此前每月 1 日 00:00–08:00 错算上月）。
- **单笔返利封顶改最大余数法**：多层合计超 `base × perConsumeCapPct` 时按缩减值最大余数分摊，整数返利之和绝不破顶（旧算法逐层四舍五入会把 0.5+0.5 进成 1+1 超封顶）。
- **并发原子性**：审批通过/拒绝改条件更新原子认领（并发/重复点击只有一个终态，重复请求 400「该申请已处理」）；建号撞手机号唯一约束返回 409 而非 500；邮箱验证码重发作废旧码（仅最新码可用，5 次连续错误作废当前码此前已有）。

- **注册校验顺序（bug12）**：`POST /api/membership/invite/register` 先做可恢复的资料校验（手机号已注册/待审占用/重复申请 → 409），全部通过后才核销邮箱验证码——**校验失败不再烧码**，用户修正资料后可用原验证码重试。验证码错误计数/5 次作废/并发占位口径不变。
- **关系树节点原型对齐**：`GET /api/admin/dist/tree` 节点（根/一级/二级同口径）新增徽章数据：`effectiveCanInvite`（有效邀请权；2026-09-01 起=本人 `canInvite` 落库值，与 `canInvite` 同值；「可邀请 · 他拿 X%」徽章用它+rebateRate）、`isActive`（「已停用」徽章）、`team`（占用中企业 `{id,name,role}`，个人计费=null；「企业管理员·团队名」徽章用 role==="ADMIN" 时渲染）、`monthTeamConsumed`（本月企业池消耗，>0 渲染「消耗来自企业共享池」）、`rebateAttribution`（本月返利归属 `[{userId,username,amount}]`：一级→根、二级→一级上级+根，实付口径，>0 才有行；空数组 → 根节点文案「无上游团队长」）；根另带 `level1Total`（「下线 N」徽章）；顶层新增 `networkCount`/`networkMonthConsumed`（树卡片头部「团队 N 人 / 计费消耗」，不含根，按筛选后口径）。见 §5.2。

### 4.4 下级账号操作

- **停用/启用 `PATCH /api/membership/invitees/:userId/status`**：`{ "isActive": false }` → `{ "id": 21, "isActive": false }`。仅限自己邀请的用户（403）。
- **重置密码 `POST /api/membership/invitees/:userId/reset-password`** → `{ "id": 21 }`。重置为系统默认密码并强制首登改密；**不返回明文、不发短信**，默认密码由邀请人线下告知（前端提示此点）。
- **下级流水 `GET /api/membership/invitees/:userId/transactions`**：参数与响应同《充值与团队功能-前端对接.md》§7.2 积分明细（查的是该下级的明细视角）。

### 4.5 申请审批

- **通过 `POST /api/membership/invite/applications/:id/approve`** → `{ "userId": 55, "status": "APPROVED" }`。被邀请人即刻成为普通用户 + 200 赠送积分（30 天），继承邀请人当时折扣；**注册时验证的邮箱会写入其账号**（用于到期提醒/收据邮件）。失败：400「该申请已处理」/「邀请名额已用完（12/12），请联系平台调整」；403「当前账号未开启邀请权限」（被后台关闭权限后存量申请也不能再放行）；409「该手机号已注册，无法通过审核」。
- **拒绝 `POST /api/membership/invite/applications/:id/reject`** → `{ "applicationId": 31, "status": "REJECTED" }`。拒绝后该手机号可被重新邀请。

### 4.6 返利提现

- **明细 `GET /api/membership/rebate/withdrawals?page=&pageSize=`** → `PageResult<{ id, amount, meta, createdAt }>`（`meta.note` 为提现说明）。
- **提现 `POST /api/membership/rebate/withdraw`**：`{ "amount": 500, "note": "提现至支付宝" }`（`amount` 正整数，不超过可提现返利）→ `{ "withdrawn": "500", "balanceAfter": "3100" }`。返利积分独立核算、不可消费，只能从这里提现；线下打款由平台处理。

### 4.7 我的邀请团队关系树 `GET /api/membership/invite/tree?page=&pageSize=`（2026-08-30 新增）

### 4.8 我的分功能用量 `GET /api/usage/my-sources?period=ALL`（2026-08-30 新增）

**代审批 `POST /api/admin/dist/applications/:id/approve` / `POST .../reject`**（无请求体）：

- 与邀请人自审**同口径**：原子认领（并发/重复 → 400「该申请已处理」）、名额校验（400 名额文案）、建号 + 200 注册赠送积分，建号归申请上的邀请人（`invitedById`），与操作人无关；

## 6. 后台 · 邀请配置 `PATCH /api/admin/users/:id/invite-config`

> 路由挂在 `admin/users` 下（不是 `/api/users`）；守卫为 JWT + **`management.users` 权限点**（2026-08-30 起，与 §5 分销管理、后台订阅调整同口径——分销代理开关本质是用户属性管理，用户管理页直接开关也走这里）。**此前是账号级充值白名单 `RechargeAccountGuard`（403「无后台充值权限」），已改**；充值白名单现在只剩真正的充值写接口（plan/pack/custom/manual/rebate-withdraw）。缺权限 403「缺少权限：用户管理」。用户列表行的「分销代理开关」即走这里。

```jsonc
{
  "canInvite": true,          // 分销代理开关（开启时若无邀请码自动生成）
  "discount": 0.8,            // 平台使用折扣 0.5~1.0，仅对「开过允许邀请注册」的账号本人生效；

  "rebateRate": 0.3,          // 一级返利比例 0~0.5
  "shareCredits": false,      // 共享额度：下级可继续消耗其额度（默认关）
  "inviteQuota": 50,          // 邀请名额（审批通过计 1）；null=不限
```

**回显来源（2026-08-30 补齐）**：邀请配置弹窗打开时的线上现状，从这两处读——`GET /api/admin/recharge/users` 列表行（新增 `subInviteAllowed`，与 `shareCredits` 等开关同 block 返回）或 `GET /api/admin/dist/tree` 的 `user` 块（§5.2，同新增）。此前 `subInviteAllowed` 只能写不能读，只改别的字段时请保持「不传该字段」的部分提交语义，避免静默覆盖。

**Response 200**（注意：**只回这几个字段**，名额/二级开关等新配置不回显，需要最新值请重拉关系树（§5.2）或用户列表（《充值与团队功能-前端对接.md》§10.1））：

## 7. 返利口径与共享额度（说明）

- **计提时机**：被邀请人本人消费（个人扣费）成功时自动计提；企业成员消耗走企业共享池时是否计提看全局开关 `corpCounts`（§5.1）。
- **层级与比例**：沿 `invitedById` 上溯最多 `maxLayers` 层（`maxLayers=null` 不限层级，上溯到底）；第 1 层 = 邀请人 `rebateRate`，第 2 层起 = 其 `level2RebateRate`（`null` 用全局默认 0.10）；`rebateEnabled=false` 的层跳过、链不断。
- **封顶**：`perConsumeCapPct`（单笔各层合计超 消耗×比例 时等比缩减）；`perInviterCap`（邀请人自然月返利入账累计封顶，当月已返部分抵扣）。
- **流水类型**：返利入账 = `REBATE_IN`（`relatedUserId`=消费者，`meta.layer` 记层级）；提现 = `REBATE_WITHDRAW`。两者都会出现在积分明细接口（《充值与团队功能-前端对接.md》§7.2），类型徽标用后端派生字段。
- **REBATE 桶**：永不过期、不可消费、仅提现；钱包可消费余额与「剩余积分」均不含它。
- **共享额度**（`shareCredits`，§6）：开启后下级在自身额度外可继续消耗邀请人额度；邀请人列表行有 `canShareFromInviter` 标志位（§4.3）。被邀请人侧的「+可用邀请人额度」展示与扣费来源细分沿用上一版《积分体系-邀请额度共享-前端对接.md》。

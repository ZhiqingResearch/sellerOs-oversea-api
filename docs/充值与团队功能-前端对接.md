# 充值与团队功能 — 前端对接文档

> 本文档可直接喂给 AI 用于前端联调。覆盖：会员充值（Stripe 微信/支付宝/银行卡三渠道）、收据中心、钱包身份视图、企业团队控制台、后台个人订阅、后台用户管理扩展。
> 邀请 / 分销（邀请注册、我的邀请、返利提现、后台分销管理、邀请配置）已拆分为独立文档《分销功能-前端对接.md》，随第二批上线使用。
> 接口统一前缀 `/api`，除特别标注「公开」外均需 Bearer JWT。本文所有字段均以后端源码实际返回为准。

## 1. 概览

### 1.1 全流程时序（下单 → 支付 → 入账 → 收据）

```text
前端                        后端                              Stripe
 │  GET /billing/catalog     │                                │
 │◀── 商品目录（价格算好）────▶│                                │
 │  POST /billing/orders     │                                │
 │◀── 订单 CREATED ──────────▶│                                │
 │  POST /orders/:orderNo/pay│                                │
 │                           │── 创建/确认 PaymentIntent ──────▶│
 │◀── 渠道支付数据 ───────────▶│                                │
 │  （用户扫码 / 跳转 / 卡表单）│                                │
 │                           │◀── webhook payment_intent.* ───│
 │                           │   （验签 → 金额核对 → 入账）      │
 │  GET /orders/:orderNo（轮询）                                │
 │                           │── 未终态时主动向 Stripe 查单同步─▶│
 │◀── status=SETTLED ────────▶│   （succeeded → 立即补入账）     │
 │  GET /billing/receipts    │                                │
 │◀── 收据列表/详情 ──────────▶│  （入账即开票 + 发收据邮件）     │
```

关键事实：

- **入账的唯一事实源是 Stripe webhook**；查单接口（`GET /orders/:orderNo`）会在订单未终态时主动向 Stripe 同步，succeeded 时立即补入账——所以前端**只管用查单接口轮询**，不需要等 webhook。
- 订单状态机：`CREATED → PENDING → PAID → SETTLED`（终态）。异常终态：`EXPIRED`（全渠道统一：发起支付后 15 分钟未支付，或 CREATED 超 15 分钟未发起支付）、`ABANDONED`（金额不符转人工）、`CANCELLED`（Stripe PaymentIntent 被取消）。前端只需关心：**`SETTLED`=成功到账；`EXPIRED/CANCELLED/ABANDONED`=关闭需重新下单**；其余为进行中。
- 入账动作按订单类型不同：个人新订阅/续费均**立即生效**（续费=有效期在原到期日上顺延 + 积分立即到账）；升档立即补差（按剩余天数折算）；充值包/自定义即时到账；团队单建队/续队（同样立即生效）/入共享池；个人转团队含折抵。SETTLED 即开票发收据邮件。
- 业务金额一律**人民币元 number**（`199` = ¥199.00；汇率 `fxRate` 如 `7.2125`）；积分仍一律**字符串**。订单/收据另带 `amountUsdCents`（实收美元美分）与 `fxRate`（1 USD = X CNY 汇率快照），两者仅发起支付后有值，否则 null。

## 2. 通用约定

### 2.1 请求头

```http
Authorization: Bearer <JWT>
Content-Type: application/json
```

### 2.2 错误格式

```ts
interface ApiError {
  statusCode: number
  message: string | string[] // 参数校验失败时为数组
  timestamp: string
}
```

常见状态码语义：

| 状态码 | 含义 |
|---|---|
| 400 | 业务校验失败（金额非法、状态不允许、名额已满等），message 为中文可直接 toast |
| 401 | 未登录 / token 失效 / 账号已停用 → 跳登录 |
| 403 | 权限不足：后台接口缺权限点（`缺少权限：用户管理`）、无后台充值权限（`无后台充值权限`）、非企业管理员（`仅企业管理员可执行该操作`）等 |
| 404 | 资源不存在或不属于当前用户（订单/收据按属主隔离，查别人的单返回 404「订单不存在」） |
| 409 | 冲突（重复申请/重复提交等） |
| 503 | 支付服务未配置（`支付服务未配置`，说明后端缺 Stripe 配置，前端应提示稍后再试） |

### 2.3 分页

请求：`page`（默认 1）、`pageSize`（默认 10，最大 100），均为 query 数字。

响应（多数列表接口）：

```ts
interface PageResult<T> {
  items: T[]
  total: number
  page: number
  pageSize: number
  totalPages: number // ⚠️ 后台个人订阅列表（§9）没有此字段
}
```

### 2.4 金额与积分

- 人民币金额：`xxxCny`（元，number；`199` = ¥199.00，汇率 `fxRate` 如 `7.2125`）。展示用 `x.toFixed(2)`。
- 美元金额：`amountUsdCents` 整数（美分，实收口径），仅发起支付后（含已入账）有值，未支付订单为 null；展示用 `(cents / 100).toFixed(2)`。
- 积分数量：Prisma Decimal 序列化为**字符串**（如 `"2380"`），可能带小数位，前端按需 `Math.floor(Number(x))` 展示。
- 自定义充值换算锚点：目录接口下发的 `creditPerCny`（1 元 = N 积分，后端固定常量 10）。

## 3. 快速接入：三种支付渠道处理要点（最容易接错，先读这里）

| | 微信 WECHAT | 支付宝 ALIPAY | 银行卡 CARD |
|---|---|---|---|
| pay 请求额外参数 | 无 | `returnUrl` **必填** | 无 |
| pay 响应关键字段 | `qrImageDataUrl` | `redirectUrl` | `clientSecret` + `publishableKey` |
| 前端动作 | 弹窗显示二维码图片 | 整页跳转 Stripe/支付宝收银台 | Stripe.js Elements 卡表单，前端自行 confirm |
| 完成判定 | 轮询查单 | 跳回 returnUrl 后轮询查单 | confirm 成功后轮询查单 |
| 超时 | 15 分钟（响应 `expiresAt`，超时订单置 EXPIRED） | 15 分钟未支付置 EXPIRED | 15 分钟未支付置 EXPIRED |

> ⚠️ **测试环境（Stripe test 模式）须知**：测试模式下微信/支付宝**无人操作也会在几分钟后被 Stripe 模拟成支付成功**（charge 上是 `mock_transaction_id`，实测微信约 6 分钟自动 succeeded），后端收到 succeeded 正常入账——这不是 bug，正式环境不会发生。要测「支付失败/未支付」路径请用：拒付卡 `4000 0000 0000 0002`（银行卡渠道），或下单后不调 pay / 不调 Stripe 页面，等 15 分钟订单自动 EXPIRED。测试模式下微信二维码的「不付款等过期」场景无法复现（Stripe 会先自动成功）。

**微信扫码步骤**：

1. `POST /orders/:orderNo/pay { "channel": "WECHAT" }`。
2. 把响应 `qrImageDataUrl`（`data:image/...;base64,...`）直接塞进 `<img src>` 弹窗展示；为 null 时提示重试。
3. 用响应 `expiresAt` 做 15 分钟倒计时；每 3–5 秒调 `GET /orders/:orderNo`。
4. `status=SETTLED` → 停止轮询，提示充值成功，刷新钱包；倒计时结束仍未 SETTLED → 停止轮询，提示「二维码已过期，请重新发起支付」（订单会被后端置 EXPIRED，需重新下单，**不要对同一订单反复 pay**——同订单同渠道重复 pay 会复用同一个 PaymentIntent，二维码不变）。
5. 用户关闭弹窗也要停止轮询。

**支付宝跳转步骤**：

1. `POST /orders/:orderNo/pay { "channel": "ALIPAY", "returnUrl": "<前端支付结果页完整 URL，建议带 orderNo>" }`，缺 `returnUrl` 返回 400「支付宝支付缺少 returnUrl」。
2. `window.location.href = redirectUrl` 整页跳转（桌面端是支付宝官方扫码收银台，手机端会唤起支付宝 App）。
3. 用户付完会被 Stripe 跳回 `returnUrl`；跳回页从 URL/本地取出 `orderNo`，开始每 3–5 秒轮询 `GET /orders/:orderNo`。若 URL 有 `payment_intent` 但 `orderNo` 缺失/为空（异常场景），先用 §5.3.1 反查恢复 `orderNo` 再轮询；反查 404 才提示「无法识别订单」并引导查看充值记录。
4. `SETTLED` → 成功页；轮询超过合理时长（建议 2 分钟）仍 PENDING → 提示「支付结果确认中，可稍后在充值记录查看」，不要重复 pay。
5. 用户中途放弃不跳回：订单 15 分钟后自动置 EXPIRED，前端无需处理。

**银行卡步骤**：

1. 页面引入 Stripe.js（`https://js.stripe.com/v3/`）。
2. `POST /orders/:orderNo/pay { "channel": "CARD" }`，拿 `clientSecret` 与 `publishableKey`。
   - `publishableKey` 为 null 说明后端未配置公钥，提示「支付暂不可用」并隐藏卡渠道。
   - `clientSecret` 只在 CARD 渠道返回；不落库到日志，前端也不要持久化。
3. 用 `publishableKey` 初始化 Stripe，**必须带 `clientSecret` 初始化 elements**（这样 `confirmPayment` 前无需 `elements.submit()`）：

   ```js
   const stripe = Stripe(publishableKey)
   const elements = stripe.elements({ clientSecret })   // ← 关键：带 clientSecret 初始化
   const paymentElement = elements.create("payment")
   paymentElement.mount("#payment-element")

   // 用户点支付：
   const { error } = await stripe.confirmPayment({
     elements,
     confirmParams: { return_url: "<前端支付结果页完整 URL，建议带 orderNo>" },
     redirect: "if_required", // 无需 3DS 的卡不跳转直接成功；3DS 卡自动走验证页
   })
   ```

   ⚠️ **不要**用 deferred 模式（`stripe.elements({ mode: "payment", amount, currency })`）挂载后又忘了 `elements.submit()`——那会报 `elements.submit() must be called before stripe.confirmPayment()`。按上面带 clientSecret 的写法就没有这个要求。若坚持用 deferred 模式，则点支付时必须先 `await elements.submit()` 成功后再 `confirmPayment`。
4. confirm 返回 `paymentIntent.status === "succeeded"`（或 `requires_capture` 等成功态）后，调 `GET /orders/:orderNo` 同步入账（查单会主动找 Stripe 核对并补入账）；之后轮询到 `SETTLED`。
5. confirm 失败展示 Stripe 返回的英文错误即可，订单保持 PENDING，用户可改卡重试（重新 pay 同渠道会复用同一 PaymentIntent）。

**轮询建议（三渠道通用）**：查单接口幂等且免费（后端向 Stripe retrieve），频率 3–5 秒一次即可；终态（SETTLED/EXPIRED/CANCELLED/ABANDONED）后必须停。不要并发轮询同一订单。

## 5. 下单 / 支付 / 查单 / 充值记录

### 试算预览 `POST /api/billing/orders/quote`（下单前先调它）

**权限**：登录用户。**只读预览：不落库、无副作用、不需要幂等键**。Body 与下单（§5.1）完全相同；与下单走**同一个算价点**，金额/积分/折抵结果天然一致；前置条件不满足（如"已有有效套餐"）在试算阶段就 400，把错误提前暴露。

**用途**：确认弹窗的金额/差价/折抵一律用它渲染，**不要**为了拿后端金额而先下单（取消弹窗会留下 CREATED 脏单出现在充值记录里）。标准流程：选商品 → `quote` → 确认弹窗 → 用户确认 → §5.1 下单 → §5.2 支付。

**Response 200**（无 orderNo/status，表示尚未成单）：

```jsonc
{
  "type": "PLAN_UPGRADE",
  "amountCny": 300,               // 应付人民币（元，后端算定）
  "creditsTotal": 2600,           // 到账积分合计
  "expiresAt": "2026-09-15T08:00:00.000Z", // 本次购买后的预计到期时刻（ISO）；充值类（PACK/CUSTOM/TEAM_PACK/TEAM_CUSTOM）为 null
  "remainingDays": 23,              // 折算所用的剩余天数（仅 PLAN_UPGRADE / TEAM_SEAT_UPGRADE / PERSONAL_TO_TEAM 有值，其余 null）；
                                    // 与 items 明细文案完全同源（升级=ceil、个人转团队=floor），「剩余 N 天」一律用它，前端不要自算（自算会有 ±1 天口径差）
  "items": [                      // 明细（折抵行 amountCny 为负），直接渲染
    { "name": "Ultra 会员升级补差（Plus → Ultra）", "detail": "按剩余 23 天折算补差，到期日不变（2026-09-15 到期）", "qty": 1, "amountCny": 230, "credits": 1993 }
  ]
}
```

**`expiresAt` 口径（后端算好，前端直接渲染，不要本地自己算日期）**：

| type | 预计到期时刻 |
|---|---|
| `PLAN_NEW` / `TEAM_PLAN` / `PERSONAL_TO_TEAM` | now + 周期（支付后立即激活/建队） |
| `PLAN_RENEW` | max（当前订阅到期， now) + 周期（续费**立即生效**：支付成功即顺延有效期、积分立即到账） |
| `PLAN_UPGRADE` / `TEAM_SEAT_UPGRADE` | 原到期日（升级不变）；补差金额/积分 = 差价 × 剩余天数/周期天数（按天折算） |
| `TEAM_RENEW` | ACTIVE 在期=max（团队到期， now)+周期（同样立即生效）；GRACE/ARCHIVED=now+周期（支付后立即恢复） |
| 充值类 | `null`（无到期概念） |

**续费的存量批次顺延（2026-08-28 起，个人/团队同口径）**：续费成功时，续费前未过期的套餐本体（PACKAGE）与套餐随赠（GIFT）批次（`RECHARGE_PLAN` 来源）会**统一延长到新有效期**——钱包/到期明细里套餐积分只剩一个到期日（新套餐到期日），不会出现「旧批次仍按原到期日清零」。充值包/自定义充值本金（本就不过期）与注册赠送、充值包赠送、客服补偿赠送按各自 30 天规则不顺延。多次续费时每次都整体顺延到最新到期日。

**PERSONAL_TO_TEAM 专有**：`items` 最多三行——① 团队版（正金额）② 个人套餐折抵（负金额，最多抵到企业价）③ 超出抵扣返还充值积分（**0 元 informational 行**，`credits`=返还积分；仅「抵扣 > 企业价」时出现，`detail` 已按 `packChoice` 写明去向「团队共享池 / 个人充值积分」）。此时 `amountCny` 为 0 → 0 元单，支付流程见 §5.2。`remainingDays` = 折抵所用剩余天数（floor，与 ② 的 detail 文案同源）。**`creditsTotal` = 池套餐+池赠送+返还积分合计（2026-08-28 起含返还行）**，与订单/收据 `totalCredits` 同口径。**折抵口径（2026-09-02 bug20 起）**：只算 PACKAGE 套餐本体——分子=个人 PACKAGE 批次剩余（仍有效），分母=该档月发放 `packageCredits`；注册赠送/套餐赠送/充值赠送/客服补偿等 GIFT 积分一律不参与折抵。**确认弹窗与支付成功弹窗必须渲染同一份下单时冻结的 `items[].detail`**（quote/下单/轮询返回的 items 同源），任何一侧都不得拿钱包余额自行重算（QA 已踩过：两弹窗「套餐积分剩余」漂移 1 积分）。

> ⚠️ **「从个人版升级到团队版」说明弹窗的剩余天数也必须用 quote 的 `remainingDays`**（或② detail 里的「剩余 N 天」文案）。说明弹窗先于确认弹窗弹出，需要在**打开说明弹窗时就调一次 quote**（只读不落单）拿值；不要拿钱包的 `expiresAt` 用 `daysLeftUntil`（ceil）本地自算——ceil 与本接口 floor 在跨日边界差 1 天，两个弹窗会对不上（QA 已踩过：说明弹窗 29 天、确认弹窗 28 天）。

**确认弹窗渲染建议（对齐原型）**：弹窗**打开时**就调 quote，拿到后一次性渲染——金额行「订阅金额 ¥199 / 30 天」（周期天数取自 catalog 的 `periodDays`）、到账积分「+2,200 积分」（用 `creditsTotal`，不拆套餐/赠送）、有效期行用 `expiresAt` 的具体日期（续费文案「在原有效期上顺延 N 天」、升级文案「保持不变」）；确认按钮也能带金额（确认订阅 · ¥199 / 确认升级 · 补差价 ¥300），因为 quote 已经返回了。

### 5.2 发起支付 `POST /api/billing/orders/:orderNo/pay`

**权限**：登录用户（仅订单属主，否则 404）。

**Body**：

```jsonc
{
  "channel": "WECHAT",        // 必填：WECHAT 微信扫码 / ALIPAY 支付宝跳转 / CARD 银行卡
  "returnUrl": "https://app.example.com/billing/result?orderNo=SR..." // ALIPAY 必填；付完跳回的前端地址，≤500 字
```

**Response 200（按渠道返回不同字段，公共字段 `orderNo` / `paymentIntentId` / `channel`）**：

```jsonc

{
  "orderNo": "SR...", "paymentIntentId": "pi_...", "channel": "WECHAT",
  "qrImageDataUrl": "data:image/png;base64,iVBOR...", // 微信二维码图片（base64 data URL），直接 <img src>；异常时为 null
  "expiresAt": "2026-08-20T14:45:00.000Z"              // 二维码有效期（15 分钟），做倒计时

// channel=ALIPAY
{
  "orderNo": "SR...", "paymentIntentId": "pi_...", "channel": "ALIPAY",
  "redirectUrl": "https://hooks.stripe.com/redirect/authenticate/src_..." // 整页跳转到支付宝收银台

// channel=CARD
{
  "orderNo": "SR...", "paymentIntentId": "pi_...", "channel": "CARD",
  "clientSecret": "pi_..._secret_...",   // Stripe.js confirmPayment 用，勿持久化
  "publishableKey": "pk_test_..."        // Stripe.js 初始化用；后端未配置时为 null

// 0 元单（PERSONAL_TO_TEAM 抵扣 ≥ 企业价，amountCny=0）：免支付直接结算，不走 Stripe；channel 传任意值均可
{
  "zeroAmount": true, "orderNo": "SR...", "status": "SETTLED"   // 已是终态：建队/折抵/清零/返还/开票全部完成，直接刷新钱包
}
```

**0 元单流程（仅 PERSONAL_TO_TEAM 可能出现）**：quote/下单 `amountCny=0` 时，前端跳过渠道选择，确认弹窗按钮文案可用「确认升级 · 无需支付」；直接调本接口（`channel` 任意），后端免支付当场入账（同事务：建队 + 折抵 + 个人套餐积分清零 + 订阅身份注销 + 超额返还 + 开票发邮件），返回 `zeroAmount: true` + `status: SETTLED`。无需轮询，不要再渲染二维码/跳转。¥0 收据照常开具并发邮件（留凭证）。

**失败**：400「订单已入账」（SETTLED）/「订单已关闭，请重新下单」（EXPIRED/CANCELLED/ABANDONED）/「支付宝支付缺少 returnUrl」；503「支付服务未配置」。

**前端处理要点**：同订单同渠道重复调用会复用已有 PaymentIntent（刷新支付页安全）；**换渠道**会新建 PaymentIntent 并覆盖订单渠道。三个渠道的前端流程见 §3。

**币种与汇率说明**：目录/订单一律人民币标价（`amountCny`）；发起支付（本接口新建 PaymentIntent 的分支）时，后端按 **Stripe 实时市场汇率**（FX Quotes base_rate）把人民币应付折成美元创建 PaymentIntent（`currency=usd`），并把此刻的汇率与折算结果快照落库（订单 `fxRate` / `amountUsdCents`，此后查单/收据沿用该快照）。复用已有 PaymentIntent 时不重新取汇率（金额已是当时快照）。用户侧实付：微信/支付宝扫码或跳转后，人民币实付金额由支付渠道按其自身汇率折算，可能与标价有微小偏差；银行卡渠道按卡组织/发卡行汇率结算。微信二维码 15 分钟有效不变。

### 5.3 查单（轮询）`GET /api/billing/orders/:orderNo`

**权限**：登录用户（仅属主）。无请求体/参数。

**Response 200**：订单视图（同 §5.1 响应），额外关注：`status`、`receiptNo`（SETTLED 后开票）、`paidAt`/`settledAt`。

行为：订单处于 CREATED/PENDING/PAID 且已有 PaymentIntent 时，后端先向 Stripe 查询——`succeeded` 则**当场入账**（效果等同 webhook，含开票发邮件），`canceled` 则置 CANCELLED，再返回最新订单。

**前端处理要点**：这是支付成功的唯一判定入口；轮询策略见 §3。`status=SETTLED` 后应刷新钱包（§7）展示新余额/新等级，并可引导查看收据（`receiptNo`）。

### 5.3.1 按 payment_intent 反查订单（支付回跳兜底）`GET /api/billing/orders/lookup?pi=pi_xxx`

**权限**：登录用户（仅属主，查别人的单同样 404）。参数：`pi` = Stripe 回跳 URL 必带的 `payment_intent` 查询参数。

**场景**：支付宝/银行卡 3DS 回跳地址丢了 `orderNo`（链接被截断等异常场景），但 `payment_intent` 一定在——用它反查出订单后，走 §5.3 正常轮询即可，用户无感。

**Response 200**：订单视图（同 §5.1 响应）。**注意本接口只读**（不向 Stripe 同步、不触发入账），拿到 `orderNo` 后必须再调 §5.3 完成同步入账。

**错误**：缺 `pi` 参数 → 400；查无此单 → 404（此时再提示「无法识别订单」并引导查看充值记录）。

普通进入充值页没有 `orderNo` 属正常，**不要**调本接口；仅当 URL 同时存在 `payment_intent` 且缺失 `orderNo` 时使用。

### 5.4 充值记录（我的订单）`GET /api/billing/records`

**权限**：登录用户。参数：`page`、`pageSize`。

**Response 200**：`PageResult<订单视图>`（含 `totalPages`），按 `createdAt` 倒序。一期只含本人订单（团队单也在购买人本人记录下）。⚠️ 列表行的 `receiptNo` 恒为 `null`（列表不带收据关联）；要看收据请去收据中心（§6.1）按订单号对应，或调 §5.3 查单接口取单个订单的 `receiptNo`。

**前端处理要点**：列表展示 `type`（类型文案前端按枚举映射）、`amountCny`（应付人民币元）、`status`、`channel`、`createdAt`。状态文案建议（三态合并为两种展示）：CREATED/PENDING/PAID=「待支付/支付中」，SETTLED=「已到账」，EXPIRED=「已过期」，CANCELLED/ABANDONED=「已关闭」（ABANDONED 为金额不符转人工单，极罕见，客服侧另有告警）。

## 6. 收据中心

> 模型：订单 SETTLED 即开票（快照冻结正文字段）并自动发收据邮件（带 PDF 附件，通道未配置时降级纯 HTML）；用户也可对后台人工充值的流水自助补开收据。**后端不提供 PDF 下载接口**：查看页用 `/html` 或直接渲染详情数据，「下载 PDF」由前端基于 HTML/数据自行生成（如浏览器打印另存 PDF、html2pdf 等）；邮件附件是后端发的，与前端无关。

### 6.5 收据 CSV 导出 `GET /api/billing/receipts/export`

**权限**：登录用户（导本人的收据）。返回 `text/csv; charset=utf-8`（带 BOM，Excel 打开中文不乱码），Blob + `a[download]` 触发下载即可。最多 5000 行，按开具时间倒序。

**Query 参数**：

| 参数 | 必填 | 说明 |
|------|------|------|
| `tz` | 否 | IANA 时区名，前端传 `Intl.DateTimeFormat().resolvedOptions().timeZone`（如 `Asia/Shanghai`）。开具时间按此时区格式化；缺省/非法回落 `Asia/Shanghai` |

**列（固定 8 列，顺序如下）**：`收据编号,订单号,开具时间,项目,支付方式,金额,接收邮箱,是否发送`

- 开具时间：`YYYY-MM-DD HH:mm:ss`（按 `tz` 时区）
- 金额：人民币、两位小数（如 `199.00`）
- 是否发送：`已发送` / `未发送`（收据邮件是否已成功寄出）
- 订单号为空（后台人工充值补开的收据）时该列为空串

```ts
// 前端调用示例
const tz = Intl.DateTimeFormat().resolvedOptions().timeZone
const res = await fetch(`/api/billing/receipts/export?tz=${encodeURIComponent(tz)}`, {
  headers: { Authorization: `Bearer ${token}` },
})
const blob = await res.blob() // 直接 Blob 下载，文件名如 receipts.csv
```

### 6.6 补开收据 `POST /api/billing/receipts/claim`

**权限**：登录用户。场景：账号曾有「后台人工充值」（客服/线下收款）流水、没有对应收据，在积分明细里点「补开收据」。

```jsonc

  "transactionId": 123,           // 积分流水 id（本人的人工充值入账行；即 /membership/transactions 返回的 id）
```

**Response 200**：收据行（含 `receiptNo`、`snapshot` 等）；已补开过同一流水则直接返回原收据（幂等）。

**`canInvite` 独立下发（2026-08-30 新增）**：`identity` 是单值（团队身份优先），无法表达「团队管理员 + 分销代理」双重身份；顶层 `canInvite` 布尔与 `identity` 解耦，所有身份都返回。邀请入口、钱包返利格、`/membership/transactions` 的 consumers 筛选等分销相关展示，一律以 `canInvite` 为准（等效于旧口径 `identity==="DISTRIBUTOR" || identity 为团队身份但本人是邀请人`）。

**到期未续费 → 自动无等级**：订阅到期后 `level` 立即按有效期推导为 `NONE`（读时生效），每日任务再把库中订阅档置空；`SUB_EXPIRED` 身份与「套餐已过期」提醒不受影响（按 `subscriptionExpiresAt` 判定）。续费/重新订阅后立即恢复对应等级。

**前端处理要点**：

- 团队身份的钱包页应展示 `team.myAvailable` 为「可用积分」、`team.poolRemaining` 为「共享池剩余」；`status=GRACE/DISABLED/ARCHIVED` 时池已冻结，展示对应 banner（GRACE 提示联系管理员续费）。
- **宽限期（GRACE）成员的可用口径（2026-08-28 明确）**：GRACE 只冻结企业共享池，**成员消费自动切换为个人积分扣减**（流水记个人口径，后端已如此，无需前端传参）。因此 `status=GRACE` 时：
  - 「当前可用积分」必须展示钱包顶层 `total`（本人个人可消费 = 充值+套餐+赠送，不含返利），并提示「企业共享积分池已冻结，当前使用个人积分计费」；
  - **不要**把 `team.myAvailable`（企业池/配额口径）当作成员整体可用积分，更不要按其值（0）在前端拦截功能——功能可用性以扣费接口实际结果为准：个人积分不足时扣费接口返回 400「积分余额不足，请充值」，此时引导「充值个人积分」即可；
  - `team.myAvailable`/`quotaRemaining`/`monthlyQuota` 仍是企业池/配额口径，供企业管理视图使用，GRACE 下不代表成员真实可用；
  - 企业续费恢复 `ACTIVE` 后，消费自动回到企业池规则，前端按 `team.status` 切回池口径展示即可。
- `nextExpireAt`/`nextExpireAmount` 用于「将于 X 日清零 N 积分」提醒条。
- **归档身份（`TEAM_ARCHIVED_*`）视图（2026-08-29 补齐归档摘要字段）**：成员已退回个人计费，左侧积分卡展示钱包顶层 `total`（含归档退回积分），badge 落「原企业已归档」（勿再显示「未订阅/你是本企业管理员」）；会员充值页按归档原型渲染（不要沿用在期企业共享池布局）：
  - 归档管理员：企业积分池「已清零」（`poolRemaining`=0）、归档前累计消耗=`poolUsedTotal`、席位=`archivedMemberCount`/`seats`、退回我的个人积分=`archiveReturned`（永不过期，已含在 `total` 内）；保留「企业团队管理」入口（只读查看成员/席位/配置/历史，见 §8）+「续费恢复团队」CTA（`TEAM_RENEW` 下单/支付链路对归档管理员正常可用，支付后立即恢复 ACTIVE，见 §5.1）；告警条「团队已归档 · 数据保留期内续费可完整恢复」（保留截止 `dataKeepUntil`）。
  - 归档成员：企业共享池「已停用」、我的个人积分=`total`、企业期间累计用量=`myPoolUsedTotal`（仅供查看）、当前计费方式=个人计费；引导订阅个人版，不给「续费企业」按钮。
- **WARN 超额策略不得前端拦截提交（2026-08-29 明确）**：`quotaMode=SHARED` 且 `overLimitPolicy=WARN` 时，`quotaRemaining`/`myAvailable`=0 只是提醒口径——成员提交功能时提示「已超本月额度」即可，**不得按 0 拦截**（后端 WARN 放行并从共享池正常扣减）。
- **BLOCK（阻止使用）是阻止企业池、不是阻止个人（2026-08-29 定稿）**：`quotaMode=SHARED` 且 `overLimitPolicy=BLOCK` 时，达限后**不再 400**——企业段只按本月配额剩余扣（扣到 0 为止），**超出部分自动从成员个人充值积分扣减**（混合扣费，明细里可见企业/个人双归属）；只有个人充值也不足时才 400「积分余额不足，请充值」。前端对 BLOCK 达限成员同样**不得拦截提交**，达限标签读 `team.limitState`/`limitStateLabel`（已限额/已超额）即可，不要自己按 quota 数字推。仅 **INDEPENDENT 独立配额**模式超额仍 400「已达本月使用上限，请联系企业管理员调整额度」（硬上限，不兜个人）。
- **左侧企业池卡片「共」口径（2026-08-29 明确）**：在期「共」= 池累计发放（钱包 `team.poolGrantedTotal` / 总览 `pool.grantedTotal`），消耗单独展示；**冻结（GRACE）/归档状态「共」= 池剩余（`team.poolRemaining` / 总览 `pool.total`，即当前冻结余额）——不得把 `poolUsedTotal`/`monthConsumed` 等历史消耗叠加进总额**（叠加会把冻结余额虚增）。要对账「发放 vs 剩余」的差额：差额 = `poolManualDeducted`（平台手动扣减）+ 已用（`poolUsedTotal`）（在期无清零时 发放-手动扣减-已用=剩余）。

### 7.2 积分明细 `GET /api/membership/transactions`

**权限**：登录用户。**记录隔离（2026-08-27 起）**：企业成员（非管理员）仅见本人流水；企业管理员 = 本人行 ∪ 本企业池行（`teamId` 相同：成员的企业段消费 + 池入账/清零/池调整），**成员的个人侧流水（个人充值记录/个人段消费行）不对管理员暴露**。池行的「使用用户」=`consumerUserId`/`consumerName`（行属主，即哪个成员操作；本人操作为 `null`/`"本人"`）；管理员可用 `consumerUserId=self|<成员userId>` 筛选（成员 id 时只看该成员的企业池行）。**本人个人历史口径（2026-10-13 调整）**：个人侧流水（`teamId` 空）在加入企业前后均可查询，不再按入队时间（`joinedAt`）裁剪。`direction=DEBIT/CREDIT` 仅筛选支出/入账，`ownership=PERSONAL/TEAM` 仅筛选个人/企业归属；显式 `startDate/endDate` 筛选仍生效。企业管理员仍只能查看本人个人流水与本企业池流水，成员仍仅查看本人可见流水，其他成员的个人记录不对管理员暴露。

参数（全可选，叠加 `page`/`pageSize`）：

| 参数 | 类型 | 说明 |
|---|---|---|
| `direction` | `CREDIT`/`DEBIT` | 入账（充值/返利）/ 出账（消费/清零） |
| `bucket` | `RECHARGE`/`PACKAGE`/`GIFT`/`REBATE` | 积分桶 |
| `type` | 流水类型 | `RECHARGE_PLAN` 套餐订阅 / `RECHARGE_PACK` 充值包 / `RECHARGE_CUSTOM` 自定义充值 / `SIGNUP_BONUS` 注册赠送 / `MANUAL_ADJUST` 手动调整 / `TEAM_RECHARGE` 企业池入账 / `TEAM_ARCHIVE_RETURN` 企业池退回 / `CONSUME` 消费 / `EXPIRE` 清零 / `REBATE_IN` 返利入账 / `REBATE_WITHDRAW` 返利提现 |
| `source` | string | 功能模块（按消费来源子串筛选，如 `listing`；下拉项见 `GET /api/usage/source-options`，尾部含非消费来源：手动调整/后台积分扣减/个人充值积分转入企业共享池/企业池调整/企业归档积分清零/套餐赠送积分清零/系统回收） |
| `startDate`/`endDate` | ISO | 时间区间（含端点） |

**混合扣费（2026-08-27 起，全消费链路通用：v1/v2/对外开放/视频结算）**：企业成员消费的扣减顺序为 **个人赠送层（PACKAGE+GIFT，会过期先烧）→ 企业共享池 → 个人充值（RECHARGE，永不过期最后扣）**。一笔消费同时动个人与企业池时称为「混合事件」，该笔的全部流水行（个人段 CONSUME + 企业段 TEAM_CONSUME，可能跨桶多行）会在 `meta` 盖同一个 `consumeEventId` + `ownershipSplit` 快照，上方归属/事件字段即由它派生。注意：配额台账只记企业段；SHARED+BLOCK「阻止使用」= 企业段按本月配额剩余封顶、超出落个人充值段（2026-08-29 定稿，不再整体报错），INDEPENDENT 维持硬上限报错。

**前端处理要点**：`scheduled=true` 打「待生效」徽标并展示 `effectiveAt`；`expired=true` 打「已过期」徽标；默认列表不含返利入账/提现（除非显式传 `type=REBATE_IN/REBATE_WITHDRAW`）。「收据」列渲染规则：`receiptNo` 有值 → 「查看收据」（跳 §6.2）；否则 `canClaimReceipt=true` → 「补开收据」（调 §6.6）；都没有 → `—`。

> 使用记录（DEBIT）「项目」列渲染：消费行展示功能标签，非消费行（清零/手动调整/后台积分扣减/转入企业池等）请兜底展示 `title`，不要显示 `—`。

### 7.3 明细筛选项 `GET /api/membership/transaction-options`

**权限**：登录用户。返回 `{ rechargeTypes, buckets, consumeSources, ownerships, consumers? }`，元素均为 `{ value, label }`，首项「全部」`value=""`（不传该参数）。`consumers`（使用用户：本人 + 各下级 / 本企业成员）仅**邀请人**或**企业管理员**有（双身份时合并去重，2026-08-27 起对企业管理员下发）；`ownerships`（积分归属：个人 PERSONAL / 企业 TEAM，2026-08-27 新增）所有用户一致下发。前端直接渲染下拉，不要硬编码。

**下拉接线（别混用）**：**使用记录 tab 的「扣费来源」下拉 → `consumeSources`**（2026-08-29 起 8 项全覆盖：个人套餐/个人充值/个人赠送/邀请人赠送/邀请人充值/企业套餐/企业充值/企业赠送积分）——行内「扣费来源」列渲染的就是 `consumeSourceLabel`，同一个词表，筛选才能选中；企业成员/管理员可见的池行（TEAM_CONSUME 消费、平台池调整扣减）同样带 `consumeSource(Label)`，企业三桶筛选项直接可用；`buckets`（充值/套餐/赠送积分）对应 `bucket` 参数，是**充值记录 tab 的积分桶筛选**，不要绑到使用记录的扣费来源上。

**充值记录 tab 的「类型」下拉 → `rechargeTypes`**（2026-08-28 起 9 项）：套餐订阅/充值包/自定义充值/注册赠送/**赠送**/手动调整/企业池入账/企业池退回。其中「赠送」是伪值 `GIFT_COMPENSATE`（= MANUAL_ADJUST 里的正向补偿发放，项目列「后台积分发放」），与「手动调整」（后台积分扣减/手动调额/差额返还等）互斥拆分——选「手动调整」不再混入赠送行。后台充值记录（`GET /api/admin/recharge/transactions`）的 `type` 参数同口径接受 `GIFT_COMPENSATE`。

```jsonc
  }
```


> 注：成员列表的 `phone` 当前为明文返回（团队内部场景），与后台用户列表的脱敏口径不同。

**添加成员 `POST /api/team/members`**：

```jsonc
{ "account": "13800138000", "username": "张三", "initialPassword": "Abcd1234" }
```

- `account`（必填）：手机号；或**已注册账号**的邮箱（邮箱仅支持拉入已存在账号，未注册邮箱返回 400「该邮箱未注册…」）。
- 已存在账号 → 直接拉入；未注册手机号 → 开新账号，`initialPassword` 必填（≥6 位，成员首次登录强制改密，`username` 缺省取账号）。
- 添加成功时自动绑定 `DEFAULT_MEMBER_ROLE_ID` 配置的平台角色（与团队内 ADMIN/MEMBER 身份独立）；已有账号保留原角色，重复绑定幂等。建号、入队、角色绑定、审计在同一事务内；默认角色配置缺失/非法/角色不存在时返回 500，操作回滚，前端无需新增参数。平台侧添加成员同规则。
- 加入即终止其个人套餐（套餐/赠送清零）、取消排队续费单、个人充值包积分保留。
- **拦截（2026-08-27 起）**：对方个人套餐/赠送积分未用完（PACKAGE+GIFT>0）→ 400「该用户的个人套餐/赠送积分未用完（剩余 X 积分），不可直接拉入企业…」——引导其在「会员充值」页走「个人转企业」自助转换（剩余价值可折抵），或待套餐积分到期清零后再添加。平台侧 `POST /api/admin/teams/:id/members` 同规则。
- **自动移出（2026-08-27 起）**：DISABLED 成员线上购买个人套餐成功后，结算时自动从企业移出（释放席位，审计记 `MEMBER_REMOVE`，actorId=0 系统）。ACTIVE 成员不触发。
- **Response**：`{ "userId": 21, "teamId": 3, "created": false }`（`created`=是否新开户）。
- **失败**：400「该用户已是本团队成员」/「该用户已归属其他企业，不可重复加入」/「席位已满，请先升级席位」/「团队当前状态不可添加成员」/「新成员需设置初始密码（至少 6 位）」/「个人套餐/赠送积分未用完…」/「该账号已停用，不可加入企业团队」（平台已停用账号 `isActive=false` 不可拉入，2026-08-28 起拦截）。

**移出成员 `DELETE /api/team/members/:userId`** → `{ "userId": 21, "removed": true }`；退回个人计费。管理员不可移出（400「管理员不可移出，请先指定新管理员」）。

**设角色 `PATCH /api/team/members/:userId/role`**：`{ "role": "ADMIN" | "MEMBER" }` → `{ "userId": 21, "role": "ADMIN" }`。设为 ADMIN = 移交管理员（原管理员自动降为成员）；当前管理员不能直接降为 MEMBER（400，须先移交）。

**停用/启用 `PATCH /api/team/members/:userId/status`**：`{ "status": "ACTIVE" | "DISABLED" }` → `{ "userId": 21, "status": "DISABLED" }`。管理员不可停用（400）；停用后不可消费；启用前若已加入他企返回 400。

**调个人月度上限 `PATCH /api/team/members/:userId/quota`**：`{ "monthlyQuota": 5000 }`（整数 ≥1；**传 `null` = 不限**，字段必须带）→ `{ "userId": 21, "monthlyQuota": 5000 }`。

**批量分配 `POST /api/team/members/batch-quota`**：`{ "monthlyQuota": 5000 | null }` → `{ "affected": 3, "monthlyQuota": 5000 }`。统一设置所有 MEMBER 角色成员（不覆盖管理员）。

**校验（400，message 可直接 toast）**：`modules` 须恰好覆盖注册表全部 9 个 moduleKey（缺 →「缺少模块配置：…」；多 →「未知的功能模块：…」；重复 →「模块配置存在重复的 moduleKey」）；全局默认三项须为对应类型的在架模型；每模块 `allowedModels` ≥1 且全部在架、类型与模块 `kind` 匹配；`defaultModel` ∈ `allowedModels`。

**前端处理要点**：

- 进入配置页并行拉 `GET /team/models/catalog`（选项池）+ `GET /team/models`（当前配置）；编辑后整页一次 `PUT /team/models`，不要逐模块提交。
- GET 返回 `allowedModels=null` 的模块，前端可在本地展开为「跟随全局默认」（如可选范围=目录中该类型全部模型、默认=全局默认），提交时须展开成具体数组（保存接口不收 null）。
- `memberSelectable=false` 时，对应功能页应把模型选择锁定为 `defaultModel`，不给成员更换入口。
- 模型目录由后端 seed 维护（`AiModel` 表），下架模型不再出现在 catalog；已保存配置里引用的下架模型会在下次保存时被 400 拦下，按 message 提示换掉即可。

## 12. 消费扣费（说明）

本次充值/团队功能**没有新增对外预检接口**。消费侧现状：

- 公共扣款 `POST /api/usage/deduct`（按人民币金额扣登录用户自己的积分）已有独立文档《积分公共扣款接口-前端对接.md》（v2 见《积分公共扣款接口v2-前端对接.md》）。企业成员消费走**混合扣费**（2026-08-27 起）：个人赠送层 → 企业共享池 → 个人充值，前端无感知；余额不足/超上限时 400（message 如「已达本月使用上限，请联系企业管理员调整额度」「团队版已到期，共享积分池已冻结…」「积分余额不足，请充值」），直接 toast 即可。
- 余额查询也可用 `GET /api/usage/balance`（与 §7.1 钱包核心字段同源，但**不含** `identity`/`team` 身份视图——身份相关展示请用 `GET /api/membership/wallet`）。
- 扣费来源/来源筛选项：`GET /api/membership/transaction-options`（§7.3）与 `GET /api/usage/source-options`。
